## D-003-001 租约续期与到期竞争

### 问题

当租约到期与原 owner 的续期请求并发时，平台应如何确定续期是否有效？

### 评审方案

- A：共享状态后端原子检查 generation 和有效期；只有尚未过期的当前 owner 可以续期，过期后必须通过更高 generation 重新取得处理权。
- B：允许原 owner 在到期后的宽限期内续期，只要尚未出现新 owner。
- C：以 Worker 本机心跳或本机时间为准，只要节点仍存活就允许续期。

### 最终决策

选择 A。租约权威由共享状态后端提供。当前 generation 与未过期条件必须在同一次原子裁决中成立；租约一旦过期，旧 generation 不得续期或复活，后续处理只能取得更高 generation。

### 判断逻辑

- B 引入宽限期后，旧 owner 与新 owner 的合法性边界会随时钟和请求顺序变化，增加双 owner 风险。
- C 依赖节点本机时间和存活判断，无法抵抗网络分区、进程暂停和时钟偏差。
- A 提供唯一权威裁决点，能与 fencing generation 共同保证同一时刻最多一个有效 owner。

### 边界场景与验收

- 续期先被共享后端原子接受：原 owner 保持当前 generation，新节点不得接管。
- 到期先被共享后端确认：原 owner 续期失败，只能停止业务写入。
- 到期与续期并发：后端只能返回一个明确结果，不允许双方都成功。
- 旧 owner 在暂停后恢复：即使本机认为租约仍有效，也不得续期或写入。
- 后端无法确认续期结果：Worker 不得假定续期成功，应停止进入新的业务阶段；是否已经开始 Agent 按 outcome_unknown 规则处理。

### 后续证据

- 契约测试：当前 generation 未过期续期成功；已过期、错误 generation 和后端结果不确定时续期失败。
- 并发测试：续期与接管竞争至少重复 50 组，任何一组有效 owner 数量不得超过 1。
- 故障注入：进程暂停、时钟偏差和共享状态短暂不可用时，旧 owner 写入成功数为 0。

## D-003-002 旧 generation 的 fencing 与审计

### 问题

当旧 generation 的 Worker 恢复并尝试写入时，fencing 应如何处理它产生的审计信息？

### 评审方案

- A：拒绝旧 generation 的所有业务写入，同时由当前平台身份追加独立、不可变的迟到写入拒绝审计。
- B：拒绝旧 generation 的业务写入，也不保留任何审计。
- C：允许旧节点写入普通审计，只拒绝 Session 和幂等终态写入。

### 最终决策

选择 A。旧 generation 不能写 Session、Session Event、幂等终态、业务审计终态、回复或原执行结果。平台以当前有效身份追加独立的“迟到写入被拒绝”诊断审计，该记录不可变且不能改变业务状态。

### 判断逻辑

- B 虽然阻止了迟到写，但会丢失故障定位和安全审查所需证据。
- C 允许旧 owner 写普通审计，可能借审计路径形成错误终态或污染执行证据。
- A 将业务写权限与诊断记录权限分离，既保持 fencing 安全边界，也满足失败可追踪要求。

### 边界场景与验收

- 旧 owner 写 Session、事件或幂等终态：条件写失败，业务状态保持不变。
- 旧 owner 写普通业务审计终态：被拒绝，不能覆盖当前 generation 的审计。
- 平台记录拒绝事件：使用当前有效平台身份，关联旧 generation、当前 generation、tenant、session 和 trace。
- 诊断审计写入失败：不得因此放行旧 owner，也不得修改已提交业务终态。
- 重复的迟到写尝试：可以形成可去重或可计数的诊断证据，但不能产生重复业务事件或回复。

### 后续证据

- 契约测试：所有带旧 generation 的权威业务写入均被拒绝。
- 集成测试：迟到写拒绝后 Session、幂等终态和回复保持不变，且可查询对应诊断审计。
- 隔离测试：诊断审计严格受 tenant/session/trace 作用域约束，不泄露其他租户记录。

## D-003-003 节点接管的执行开始证据

### 问题

节点租约失效后，新节点应根据什么证据判断原 Agent 尚未开始、因此可以安全接管执行？

### 评审方案

- A：调用 Agent 前，由当前 owner 以 generation 条件写持久记录 EXECUTION_STARTED；只有共享状态明确处于该阶段之前才允许换代接管。
- B：根据原 Worker 的存活或心跳判断；节点失联即允许接管。
- C：租约到期后一律重新执行，依赖最终幂等提交抑制重复结果。

### 最终决策

选择 A。共享幂等记录是执行阶段的权威证据。当前 owner 必须先成功写入 EXECUTION_STARTED，再调用 Agent；写入结果不确定时不得调用。新节点只有在共享状态明确证明 Agent 尚未开始时才能取得更高 generation 并接管，无法确认时进入 outcome_unknown。

### 判断逻辑

- B 只能证明节点不可达，不能证明 Agent 未开始或未产生副作用。
- C 只能抑制重复终态，不能撤销 Agent、Tool 或外部依赖已经产生的重复副作用。
- A 在不可避免的进程退出窗口中选择“宁可结果待人工确认，也不自动重复执行”，与第二阶段的安全重试边界一致。

### 边界场景与验收

- EXECUTION_STARTED 条件写成功前节点退出：旧租约确认失效后，新 generation 可以接管。
- EXECUTION_STARTED 写入结果不确定：原节点不得调用 Agent，新节点按 outcome_unknown 处理，除非后端恢复后能明确读到开始前状态。
- EXECUTION_STARTED 已确认后节点退出：禁止相同 external_message_id 自动重放。
- Worker 心跳中断但租约未失效：其他节点不得接管。
- Worker 仍存活但租约已失效：旧 generation 不得继续执行或写入。

### 后续证据

- 状态机测试：只有开始前状态允许 takeover，EXECUTION_STARTED 及未知状态均拒绝重放。
- 故障注入：在开始标记写入前、写入中和写入后分别终止节点，验证接管结论唯一。
- 并发测试：节点接管与旧 owner 开始执行竞争时，Agent 调用次数最多为 1。

## D-003-004 跨后端部分提交恢复

### 问题

当持久化审计已经成功，但共享幂等终态写入超时或结果无法确认时，平台应如何响应并恢复？

### 评审方案

- A：返回 outcome_unknown 并禁止重放；持久化恢复记录保存既有结果或安全引用，恢复流程仅条件补齐幂等终态。
- B：审计成功即向调用方返回成功，后台尝试补写幂等终态。
- C：将本次视为失败，下一次重复消息重新调用 Agent。
- D：删除或回滚已写审计，再允许请求重新执行。

### 最终决策

选择 A。部分提交期间不得对外报告完整成功。持久化最终审计时同步保留足以校验和恢复既有终态的脱敏结果或安全引用；恢复流程只能条件补齐共享幂等终态，不能重新调用 Agent、重建结果或覆盖其他 generation 的终态。

### 判断逻辑

- B 会在幂等保护尚未形成可靠终态时向调用方承诺成功，后续重复请求语义不稳定。
- C 可能重复 Agent 或外部副作用，违反最多执行一次的阶段目标。
- D 依赖跨后端回滚，在没有分布式事务的边界下可能产生新的不确定状态并破坏审计证据。
- A 将业务执行与状态修复分离，恢复只复制已知结果，不再次产生业务副作用。

### 边界场景与验收

- 最终审计和恢复记录成功、幂等终态明确失败：返回 outcome_unknown，等待条件补齐。
- 幂等终态写入超时且结果未知：先读取核对；无法确认时保持 outcome_unknown，不重执行。
- 补偿时发现相同 generation 已有相同终态：按幂等修复成功处理。
- 补偿时发现不同 generation 或不同结果：停止自动修复，保留冲突证据并要求人工处理。
- 持久化恢复记录自身写入不确定：不得继续提交完整成功，也不得自动重放 Agent。

### 后续证据

- 状态机测试：所有部分提交组合均映射为唯一且安全的错误或恢复状态。
- 故障注入：在最终审计、恢复记录和幂等终态各写入点注入超时，Agent 调用次数仍最多为 1。
- 恢复测试：修复流程只补齐原结果，错误 tenant、message、trace 或 generation 条件全部拒绝。

## D-003-005 配置缓存授权边界

### 问题

当持久化配置后端暂时不可用时，Worker 是否可以使用缓存中的 Tenant 或 Channel Binding 配置授权新的消息执行？

### 评审方案

- A：后端不可用时，缓存不能授权新执行；无法确认权威配置便默认拒绝。
- B：明确短 TTL 且版本已知的正向缓存可以在后端不可用时继续授权。
- C：持续使用最后一次成功读取的配置授权，直到后端恢复。
- D：已建立的 Session 可以使用缓存授权，新 Session 必须拒绝。

### 最终决策

选择 A。持久化配置是 Tenant、Agent 和 Channel Binding 授权的权威来源。权威版本或新鲜度无法验证时，任何正向缓存都不能授予新的业务执行权限；缓存只能在权威配置可验证时加速读取、辅助诊断，或者继续维持拒绝决定。

### 判断逻辑

- B 的 TTL 只能限制陈旧时间，不能证明期间没有发生租户停用、Binding 撤销、密钥轮换或所有权变更。
- C 在后端长时间故障时会无限扩大陈旧授权窗口。
- D 让权限强度依赖 Session 是否已建立，可能使被撤销主体通过旧会话继续访问。
- A 牺牲配置后端故障期间的可用性，换取默认拒绝和租户授权边界的确定性，符合项目宪法。

### 边界场景与验收

- 后端不可用且存在启用配置缓存：拒绝新执行，不能调用 Agent。
- 后端不可用且存在禁用或拒绝缓存：可以继续拒绝，但不能因此构造其他授权结论。
- 本地 TTL 未到期但无法核对权威版本：仍然拒绝。
- 后端恢复且权威版本可读取：重新校验 tenant、Binding 所有权、启用状态和 secret reference 后才可授权。
- 多节点缓存版本不同：任一节点都必须以可验证的权威配置为准，不得因路由节点不同产生放行差异。

### 后续证据

- 授权测试：配置后端不可用时，所有正向缓存场景的 Agent 调用次数为 0。
- 变更测试：Tenant 停用、Binding 撤销、密钥引用变更后，旧缓存不能继续授权。
- 双节点测试：两个节点缓存状态不同时，只要权威配置不可验证，二者都返回同类默认拒绝。
