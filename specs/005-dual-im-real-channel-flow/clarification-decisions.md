## DEC-001：Channel Binding 身份键

### 问题

系统应使用哪组由 IM 平台认证的身份作为 Channel Binding 唯一键，才能确保相同或相似的机器人标识不会绑定到错误租户？

该问题直接影响租户身份的可信来源。如果身份键不完整，系统可能把来自不同企业的消息解析为同一绑定，造成跨租户会话、审计和数据访问风险。

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 飞书使用“渠道＋tenant_key＋app_id/bot_id”，企业微信使用“渠道＋corp_id＋bot_id” | 身份边界完整，支持同企业多机器人和跨企业隔离 |
| B | 只使用“渠道＋app_id/bot_id” | 实现简单，但没有显式验证机器人所属企业 |
| C | 只使用“渠道＋tenant_key/corp_id” | 可以区分企业，但无法区分同一企业内的多个机器人 |
| D | 只使用人工配置的 binding_id | 无法证明消息携带的平台身份与人工绑定一致 |

### 最终决定

选择方案 A。

- 飞书 Channel Identity：`feishu + tenant_key + app_id/bot_id`。
- 企业微信 Channel Identity：`wecom + corp_id + bot_id`。
- 所有组成部分必须来自 SDK 已认证的事件或连接上下文。
- 任一组成部分缺失、来源不可信或与持久化绑定不一致时，系统默认拒绝。
- tenant_id 只能由成功匹配的 Channel Binding 得出，不能从消息正文或外部请求参数中采信。

### 判断依据

1. 项目宪法要求租户身份必须可验证，并且访问控制默认拒绝。
2. 企业身份与机器人身份共同参与匹配，可以同时防止跨企业误绑定和同企业多机器人冲突。
3. 将渠道类型加入键中，可以防止飞书和企业微信出现相同外部标识时发生碰撞。
4. 该方案使 Channel Binding 成为唯一可信的租户解析边界，Gateway 无需信任外部 tenant_id。
5. 虽然复合键比单字段键稍复杂，但增加的存储和查询成本很小，安全收益明显更高。

### 对实现的影响

- Channel Binding Repository 需要支持按复合 Channel Identity 精确查询。
- 飞书 Adapter 必须从已认证上下文提取 tenant_key 和应用/机器人身份。
- 企业微信 Adapter 必须从已认证上下文提取 corp_id 和 Bot ID。
- 统一入站消息只能携带可信身份字段，不允许 Adapter 自行填入业务 tenant_id。
- 数据库需要对复合身份建立唯一约束，避免重复绑定。

### 对测试和验收的影响

- 验证正确复合身份能够解析到预期租户。
- 分别修改企业身份、机器人身份和渠道类型，均应得到默认拒绝结果。
- 验证相同外部机器人标识在不同企业之间不会共享 Session、幂等记录或 Audit Log。
- 验证同一企业的多个机器人可以绑定到不同配置且不会相互覆盖。
- 所有拒绝路径的 Agent 调用次数必须为 0，并生成不含凭证的安全审计记录。

## DEC-002：群聊 Session 边界

### 问题

同一群聊中的不同成员分别 @ 机器人时，是共享整个群的 Agent 历史上下文，还是为每位发送者建立独立的多轮会话？

如果共享群上下文，一名成员的历史问题、身份信息或业务数据可能被带入另一名成员的 Runner 输入；如果完全不保留上下文，又无法满足群聊中的多轮交互。

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 按“租户＋渠道＋绑定＋群聊＋发送者”建立 Session | 同群成员相互隔离，同时保留个人多轮上下文 |
| B | 整个群共享一个 Session | 便于形成群体上下文，但存在串话和隐私泄露风险 |
| C | 每条群消息创建新 Session | 隔离最强，但完全失去多轮上下文 |
| D | 由 Channel Binding 动态配置，默认按发送者隔离 | 最灵活，但增加本阶段配置、分支和测试复杂度 |

### 最终决定

选择方案 A。

群聊 Session 键至少包含：

`tenant_id + channel_type + channel_binding_id + group_conversation_id + sender_id`

同一成员在同一群聊中可以延续多轮上下文；同一群聊中的不同成员必须使用不同 Session。机器人回复仍发送到原群聊，但 Runner 输入只读取当前发送者所属 Session 的历史记录。

### 判断依据

1. 优先满足项目宪法规定的租户隔离与最小披露原则。
2. 避免群成员之间无意共享历史问题、业务数据和 Agent 状态。
3. 与现有 tenant-scoped Session 机制兼容，只需扩展稳定的会话键构造规则。
4. 相比每条消息新建 Session，该方案仍然支持有价值的群聊多轮交互。
5. 当前阶段不引入可配置共享群上下文，减少实现和验收分支；如以后确有协作场景，可作为独立功能评审。

### 对实现的影响

- 两个 Channel Adapter 都需要识别单聊与群聊，并在群聊消息中提取稳定的群聊标识和发送者标识。
- Session Key Builder 需要为群聊使用群聊与发送者组合键。
- Adapter 不得把群聊标识单独当作 Session ID。
- 回复目标仍然是原群聊，不能因为 Session 按发送者隔离而改成私聊回复。

### 对测试和验收的影响

- 同一群聊中用户 A 的第二轮消息应读取用户 A 的第一轮上下文。
- 同一群聊中用户 B 的首轮消息不得读取用户 A 的上下文。
- 两位用户发送相同文本或相同局部标识时，Session 和幂等记录不得碰撞。
- 审计记录必须同时包含群聊标识和发送者标识，并继续按 tenant_id 隔离。

## DEC-003：渠道回复重试

### 问题

Agent 结果已经持久化，但飞书或企业微信回复发送失败或超时时，系统应如何重试，才能恢复交付且不重复执行 Agent 或重复回复用户？

回复失败不等于 Agent 执行失败。若把两者混为同一状态，恢复时可能重复调用 Agent；若对所有超时直接重发，又可能在平台实际已接收消息的情况下产生重复回复。

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 按失败类型分类；临时失败有限重试，永久失败终止，结果未知不自动重发 | 同时控制丢失、重复发送与重试风暴风险 |
| B | 所有失败和超时都自动重试 3 次 | 实现简单，但未知超时可能造成重复回复 |
| C | 所有失败均不自动重试 | 不会重复发送，但短暂网络故障也无法自动恢复 |
| D | 持续重试直到成功 | 恢复概率较高，但可能形成无界重试和资源占用 |

### 最终决定

选择方案 A。

- 明确临时失败：分别等待 1、2、4 秒，最多自动重试 3 次。
- 永久失败：不自动重试，最终状态记为 `delivery_failed`。
- 发送超时且无法判断平台是否已经接收：状态记为 `delivery_unknown`，不得自动重发。
- Agent 结果一旦持久化，所有发送重试、状态收敛和显式恢复都只能复用该结果，不得再次调用 Agent。
- 每次发送均形成独立 Delivery Attempt，并记录脱敏错误和 trace 关联。

### 判断依据

1. 区分“业务执行结果”和“渠道交付结果”，符合第三阶段部分提交恢复原
2. 则。
3. 对明确临时故障有限重试，可以覆盖常见瞬时网络和限流问题。
4. 对未知超时禁止自动重发，可以避免平台已经接收但客户端尚未确认时产生重复回复。
5. 对永久失败及时终止，避免无意义重试和资源浪费。
6. 固定退避与次数便于自动化测试、审计解释和答辩展示。

### 对实现的影响

- 需要建立回复交付状态和 Delivery Attempt 持久化模型。
- 渠道 SDK 错误必须被映射为临时失败、永久失败或结果未知。
- 回复恢复任务只能读取已持久化的统一回复，不得进入 Runner 调用路径。
- `delivery_unknown` 只能通过平台确认、状态收敛或显式恢复流程处理。

### 对测试和验收的影响

- 注入明确临时失败，验证 1、2、4 秒退避和最多 3 次自动重试。
- 注入永久失败，验证自动重试次数为 0，状态为 `delivery_failed`。
- 注入发送超时，验证自动重发次数为 0，状态为 `delivery_unknown`。
- 所有回复恢复场景中，Agent 额外调用次数必须为 0。
- Audit Log 能够查询每次 Delivery Attempt、最终状态和脱敏错误。

## DEC-004：长连接高可用

### 问题

同一个飞书 App 或企业微信 Bot 在多个 Adapter 节点部署时，应由哪个节点建立和持有长连接，节点中断后又如何安全接管？

如果多个节点同时连接，可能违反 SDK 或平台连接限制并造成重复事件和回复；如果固定在单节点，节点中断后渠道会完全不可用。接管过程中还必须阻止已经失去所有权的旧节点继续发送消息。

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 每个 Channel Identity 使用共享租约选出唯一活动节点，备用节点在租约失效后接管 | 支持自动恢复，并可使用 fencing 阻止旧节点继续操作 |
| B | 固定单节点运行 Adapter | 实现最简单，但没有自动故障恢复 |
| C | 多节点同时连接同一 App 或 Bot | 表面上可并行，但可能违反连接限制并产生重复处理 |
| D | 飞书和企业微信分别使用不同高可用模型 | 能利用平台差异，但增加本阶段实现、运维和测试复杂度 |

### 最终决定

选择方案 A。

- 每个 Channel Identity 同时最多只有一个活动 Adapter 节点。
- 只有共享所有权租约持有者可以建立和维持长连接。
- 备用节点不接收业务流量，在租约失效后竞争接管。
- 接管成功时递增 generation，并为新所有者签发新的 fencing token。
- 旧节点一旦失去租约，必须退出就绪状态、关闭连接，并停止新的状态写入和回复发送。

### 判断依据

1. 复用第三阶段已经设计和验证的共享租约、generation 与 fencing 机制。
2. 避免多个连接相互挤占、重复接收事件或重复发送回复。
3. 相比固定单节点，主动/备用可以在节点中断后自动恢复渠道能力。
4. 统一两种 IM 的高可用模型，可以降低实现、部署和验收复杂度。
5. fencing 将“连接是否仍存活”和“节点是否仍有业务所有权”分离，能够处理网络分区和暂停后恢复的旧节点。

### 对实现的影响

- Redis 或等价共享后端需要保存按 Channel Identity 划分的 Adapter Ownership Lease。
- 租约至少包含 owner_node_id、generation、fencing_token 和 expires_at。
- Adapter 只有取得租约后才能进入就绪状态并启动 SDK 长连接。
- 续租失败或发现更高 generation 后，Adapter 必须停止接收并关闭连接。
- 回复发送和相关持久化写入必须校验当前 fencing token。

### 对测试和验收的影响

- 同时启动两个 Adapter 节点时，活动连接数量必须为 1。
- 终止活动节点后，备用节点应在租约失效和重连预算内完成接管。
- 模拟旧节点恢复后，其旧 fencing token 的写入和回复必须全部被拒绝。
- 接管期间平台重放的消息必须继续通过共享幂等控制，Agent 最多执行一次。
- Audit Log 必须记录租约取得、续租失败、所有权转移和旧节点拒绝事件。

## DEC-005：机器人自身消息过滤

### 问题

Adapter 收到机器人自身发送的消息，或者 SDK 事件中的发送者身份不完整、无法确认是否为当前机器人时，应当如何处理？

如果机器人把自己的回复再次交给 Agent，可能形成无限回复循环并持续消耗资源。若依赖消息文本、机器人名称或固定前缀判断，又容易被普通用户伪造或因名称变化而误判。

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 使用 SDK 认证身份严格比较；自身消息忽略，身份不确定时默认拒绝 | 安全边界清晰，可阻止循环和伪造 |
| B | 根据消息内容、机器人名称或固定前缀判断 | 实现简单，但不可信且容易误判 |
| C | 假设平台不会推送自身消息，不增加过滤 | 依赖外部平台隐含行为，故障时可能形成循环 |
| D | 所有消息进入 Gateway，依靠幂等阻止循环 | 自身回复通常具有新消息 ID，幂等无法可靠阻止 |

### 最终决定

选择方案 A。

- Adapter 使用 SDK 已认证的 sender_type、sender_id 和当前运行时机器人身份进行比较。
- 确认发送者是当前机器人时，静默忽略该消息。
- 发送者身份字段缺失、来源不可信或无法确认时，默认拒绝并记录安全审计。
- 上述两种路径都不得创建业务 Session、调用 Agent 或发送业务回复。
- 禁止使用消息正文、机器人名称、显示昵称或自定义文本前缀判断自身身份。

### 判断依据

1. 平台认证身份比消息内容和显示名称更可信。
2. 自身消息通常会产生新的外部消息 ID，不能仅依赖幂等机制阻止循环。
3. 身份无法确认时默认拒绝，符合项目宪法的安全默认策略。
4. 在 Adapter 入口过滤，可以避免无效消息污染 Gateway、Session、幂等状态和 Runner。
5. 安全审计能够保留异常证据，同时不向群聊或单聊继续发送消息。

### 对实现的影响

- Adapter 启动和认证完成后需要保存当前机器人运行时身份。
- 统一消息转换前必须先完成发送者身份完整性校验和自身消息判断。
- 飞书和企业微信 SDK 字段需要分别映射到统一的认证发送者身份。
- 自身消息采用可观察的忽略状态；身份不确定采用稳定的安全拒绝状态。

### 对测试和验收的影响

- 构造发送者为当前机器人的事件，验证 Agent 和业务回复调用次数均为 0。
- 构造缺失 sender_type、sender_id 或机器人运行时身份的事件，验证默认拒绝。
- 普通用户发送包含机器人名称或回复前缀的文本时，不得被误判为自身消息。
- 使用新的 message_id 或 msgid 模拟机器人自身回复，仍必须在 Adapter 入口被过滤。
- 身份不确定路径必须产生脱敏安全审计，自身消息不得形成新的业务 Session。
