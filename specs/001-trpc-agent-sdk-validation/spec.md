# Feature Specification: tRPC-Agent SDK 最小集成验证

**Feature Branch**: `not-created (Git repository unavailable)`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "生成第一份 SDK 验证规格，证明作业仓库能够直接使用固定版本的 tRPC-Agent-Python，离线跑通最小 Agent 执行、事件输出和多轮会话，不依赖真实 API Key。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 验证官方 SDK 最小执行链路 (Priority: P1)

作为项目开发者，我希望在作业仓库中运行一个最小、确定性的验证场景，证明项目能够加载指定版本的 tRPC-Agent-Python，并通过该框架的正式执行链路接收一条用户消息、产生执行事件和最终回复，从而确认后续平台开发具有可用的框架基础。

**Why this priority**: 这是整个项目“基于 tRPC-Agent-Python”这一前提的最小证据。如果该链路不成立，后续多租户、Gateway、IM 和存储设计都缺少可靠的运行基础。

**Independent Test**: 在不配置任何真实模型凭据的环境中启动验证，提交一条固定消息；验证过程完成且返回预期的最终回复，同时明确报告实际加载的 SDK 版本。

**Acceptance Scenarios**:

1. **Given** 项目依赖已准备完成且未配置真实模型凭据，**When** 开发者运行最小验证并提交一条消息，**Then** 系统通过官方 SDK 执行链路产生至少一个可观察事件，并返回唯一、非空且符合预期的最终回复。
2. **Given** 目标 SDK 版本为 `1.1.19`，**When** 验证开始，**Then** 验证结果明确显示实际加载版本为 `1.1.19`，版本不一致时验证失败并说明期望值和实际值。
3. **Given** 验证环境未提供外部模型访问条件，**When** 完成整个验证，**Then** 不发生真实模型请求、不要求 API Key，也不产生模型调用费用。

---

### User Story 2 - 验证同一会话的连续执行 (Priority: P2)

作为平台架构开发者，我希望连续发送两轮属于同一会话的消息，并确认第二轮执行仍能访问第一轮留下的会话信息，从而证明框架的会话能力可以作为后续跨节点和多后端设计的基础。

**Why this priority**: 多租户平台后续需要围绕 Session 进行路由、持久化和并发控制；在平台封装前必须先确认框架原生会话语义可被稳定观察和验证。

**Independent Test**: 使用一个全新的会话依次提交两条相关消息，验证两轮均产生最终回复，且第二轮结果包含预先约定的第一轮信息；该测试无需依赖 User Story 1 的历史运行数据。

**Acceptance Scenarios**:

1. **Given** 一个不存在历史数据的新会话，**When** 开发者依次提交两条相关消息，**Then** 两轮执行均成功完成并分别产生一个可识别的最终回复。
2. **Given** 第一轮消息包含测试约定的会话信息，**When** 同一用户在同一会话中执行第二轮，**Then** 第二轮结果能够反映该信息，证明会话上下文连续。
3. **Given** 两个不同的会话标识，**When** 它们执行相同的两轮验证，**Then** 两个会话互不读取对方留下的信息。

---

### User Story 3 - 获得可重复、可诊断的验证结果 (Priority: P3)

作为项目维护者或评审者，我希望通过一个有明确说明的入口重复运行 SDK 验证，并在失败时快速判断是版本、初始化、事件处理还是会话连续性出了问题，从而让验证结果能够作为后续升级和答辩材料的可信证据。

**Why this priority**: 一次偶然成功不足以证明集成可靠；可重复运行和清晰诊断可以防止 SDK 升级或环境变化悄悄破坏平台基础。

**Independent Test**: 在清理验证产生的临时状态后连续运行两次，确认结果一致；随后人为制造版本不匹配或缺少最终事件的情况，确认失败报告能指出对应阶段。

**Acceptance Scenarios**:

1. **Given** 相同的项目版本和干净验证状态，**When** 连续运行两次完整验证，**Then** 两次得到相同的通过项、事件结论和最终回复。
2. **Given** SDK 版本与目标基线不一致，**When** 运行验证，**Then** 验证以失败结束并明确标识版本检查阶段，而不是继续产生误导性的成功结果。
3. **Given** 执行过程结束但没有产生可识别的最终回复，**When** 验证汇总结果，**Then** 验证失败并保留足以定位事件处理阶段的非敏感信息。

---

### Edge Cases

- 实际安装的 SDK 能够被加载，但版本与目标基线不一致。
- 执行过程产生零个事件、多个候选最终回复，或仅产生错误事件。
- 第一轮成功而第二轮失败，或者第二轮无法读取第一轮约定的信息。
- 不同会话之间意外共享了状态，导致隔离断言失败。
- 上一次运行残留的会话状态影响下一次验证，使结果不可重复。
- 离线替代能力配置错误并尝试访问外部模型服务。
- 回复内容为空、只有空白字符，或者执行异常被吞掉后仍报告成功。
- 事件结构与预期不兼容时，验证应明确失败，而不是依赖未检查的字段继续运行。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 项目 MUST 明确声明本次验证针对的 tRPC-Agent-Python 基线版本为 `1.1.19`，并在每次验证中核对实际加载版本。
- **FR-002**: 验证 MUST 真实经过官方 SDK 提供的 Agent 执行、事件输出和会话管理能力，不得用平台自定义实现替代被验证的框架路径。
- **FR-003**: 验证 MUST 在没有真实模型 API Key、没有真实模型调用且不产生模型费用的条件下完成。
- **FR-004**: 验证 MUST 使用确定性输入与确定性回复规则，使相同环境下的重复运行产生一致结论。
- **FR-005**: 验证 MUST 支持提交一条用户消息，并断言执行过程至少产生一个事件和一个唯一、非空的最终回复。
- **FR-006**: 验证 MUST 收集本次执行产生的事件，并能够区分中间事件、最终回复和错误结果。
- **FR-007**: 验证 MUST 支持同一用户、同一会话的连续两轮执行，并验证第二轮能够使用第一轮约定的会话信息。
- **FR-008**: 验证 MUST 证明不同会话标识之间的测试状态相互隔离。
- **FR-009**: 验证 MUST 能够在干净状态下重复运行，不依赖其他测试的执行顺序或此前残留的数据。
- **FR-010**: 项目 MUST 提供一个有文档说明的统一验证入口，并说明运行前提、预期结果和成功判定方式。
- **FR-011**: 验证失败时 MUST 明确报告失败发生在版本检查、Agent 初始化、消息执行、事件识别或会话连续性中的哪个阶段。
- **FR-012**: 验证输出 MUST 避免显示或持久化凭据、访问令牌及其他敏感配置；即使环境中意外存在这些值也不得输出。
- **FR-013**: 验证结果 MUST 留下可供代码评审和后续 SDK 升级比较的自动化通过/失败证据。

### Key Entities

- **SDK 基线**: 本功能需要验证的框架发行版本，以及运行时实际识别出的版本。
- **验证运行**: 一次独立验证活动，包含运行标识、检查阶段、通过/失败状态和非敏感诊断结果。
- **测试会话**: 用于承载一轮或多轮测试消息的隔离上下文，由用户标识和会话标识共同确定。
- **执行事件**: 框架在处理消息时产生的可观察结果，至少能区分中间过程、最终回复和错误。
- **验证证据**: 自动化检查产生的版本、事件、最终回复、会话连续性及隔离性结论。

## Scope Boundaries

### Included

- 固定并核对一个明确的 tRPC-Agent-Python SDK 基线。
- 离线验证最小消息执行、事件收集、最终回复识别和两轮会话连续性。
- 自动检查不同测试会话之间的状态隔离。
- 提供可重复运行说明和可诊断的验证结果。
- 记录本功能直接复用的框架能力，为后续平台设计提供证据。

### Excluded

- 真实大模型供应商接入、真实 API Key 和模型效果评估。
- HTTP 服务、Web 页面、Agent Gateway、Worker 调度和 Admin API。
- 多租户数据模型、租户鉴权和租户级配置加载。
- Redis、SQL、向量库、对象存储及跨节点状态共享。
- 企业微信、WebSocket 或其他 IM Channel Adapter。
- Knowledge、Memory、Tool、Filter、Telemetry 等后续平台能力的完整验证。
- 性能、压力、容灾和生产部署验证。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新开发者按照项目说明，能在 10 分钟内完成一次 SDK 验证并判断整体结果是通过还是失败。
- **SC-002**: 自动化验证对单轮回复、两轮会话连续性和跨会话隔离三个核心场景的检查通过率达到 100%。
- **SC-003**: 每次成功运行都明确报告目标版本和实际版本，且两者均为 `1.1.19`。
- **SC-004**: 完整验证在零真实模型请求、零模型调用费用和零必需外部凭据的条件下完成。
- **SC-005**: 在相同干净环境中连续运行两次，核心场景的通过/失败结论和预期回复一致率达到 100%。
- **SC-006**: 对版本不匹配、缺少最终回复和会话连续性失败三类故障，验证结果均能在一次运行内指出对应失败阶段。
- **SC-007**: 自动化验证输出和保存的验证证据中，敏感凭据泄露数量为 0。

## Traceability

- **README 验收标准 7**: 本功能证明 Agent 执行、事件输出和 Session 管理由
  tRPC-Agent-Python 直接提供，并通过离线兼容性测试形成证据；多租户、Gateway、
  Channel Adapter、Storage Adapter 等平台新增能力明确不属于本功能。
- **Constitution v1.0.0**: 本功能受全部项目原则约束，重点落实
  Framework-First、Security by Default 和 Spec-Driven Evidence；InMemory 仅用于
  本地验证，不构成生产共享状态方案。

## Assumptions

- 本功能面向项目开发者、维护者和技术评审者，不面向最终企业用户。
- 本地参考仓库用于核对 SDK 行为和版本，作业仓库通过正式发行依赖使用框架，不复制或修改参考仓库源码。
- 本地参考源码当前声明版本为 `1.1.19`，并将该版本作为第一阶段兼容性基线。
- 验证环境满足目标 SDK 官方支持的运行前提；具体环境和依赖管理方式在后续计划阶段确定。
- 为保证离线、无费用和确定性，验证允许使用受控的模型替代能力，但 Agent 执行、事件输出和会话管理必须来自官方 SDK。
- 本功能只验证会话级上下文连续性，不把长期用户记忆或知识检索视为 Session 验证的一部分。
- 项目 Constitution v1.0.0 已于 2026-09-03 批准，本规格及其后续 Plan、Tasks 和
  实现均以该版本为治理基线。
- 本功能依赖目标 SDK 发行包可被开发环境取得；依赖获取失败属于环境准备问题，但必须被清楚报告，不能被误判为功能验证通过。
