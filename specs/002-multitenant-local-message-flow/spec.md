# Feature Specification: 多租户本地消息闭环

**Feature Branch**: `feature/luwenjie`

**Created**: 2026-09-05

**Status**: Complete — implementation and acceptance evidence verified

**Input**: User description: "实现一个本地可运行的纵向链路：HTTP Channel Adapter → Gateway → 租户与 Channel Binding 校验 → 消息幂等 → tenant-scoped Session → Agent Worker → 官方 tRPC-Agent Runner → 统一回复 → Audit Log。覆盖两个租户隔离、同租户多轮会话、拒绝非法租户和绑定、重复消息幂等、trace_id 贯穿与审计；本阶段仅使用可替换的 InMemory 存储，不包含真实 IM、共享后端、Kubernetes、真实模型 API 或管理后台。"

## Clarifications

### Session 2026-09-05

- Q: 同一租户会话的两条不同消息同时到达时，平台应该采用哪种处理顺序？ → A: 同一会话串行执行，不同会话可以并行。
- Q: 首次消息处理失败后，相同 external_message_id 再次投递时，平台应该允许重新执行 Agent 吗？ → A: Agent 开始前失败可重试，开始后失败或结果不确定不可重试。
- Q: 本地 HTTP 调用方应该如何证明自己有权使用指定的 Channel Binding？ → A: 每个绑定使用 HMAC 请求签名和时间戳。

### Consistency Review 2026-09-05

- Q: Channel Binding 改绑到另一个 Agent 后是否继续旧会话？ → A: 不继续；Agent 是会话身份的一部分，改绑后生成新平台会话。
- Q: 如何判定 Agent 已经开始，从而决定相同消息是否可重试？ → A: Worker 完成可失败的准备后，Gateway 将幂等状态标为 RUNNING；首次请求 Runner Event 即视为开始。RUNNING 后的超时或取消按结果不确定处理。
- Q: 最终审计和幂等终态以什么顺序提交？ → A: 幂等记录保持 RUNNING，先可靠写入最终审计，再条件提交业务终态；最终审计失败保存为不可重放的执行后失败，终态提交不确定保存为 OUTCOME_UNKNOWN。
- Q: 审计和指标如何保持租户隔离？ → A: 认证后的 append、update 和 query 必须显式携带租户作用域；预认证拒绝只允许使用受限的 system/pre-auth scope。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 发送一条可审计的租户消息 (Priority: P1)

作为已绑定本地消息通道的租户用户，我希望消息被路由到本租户指定的 Agent，并收到
统一格式的回复，使我能够通过一个本地入口演示从消息接入到 Agent 执行的完整链路。

**Why this priority**: 这是本阶段最小业务闭环；没有成功消息链路，其余隔离、幂等和
审计能力都没有可验证的业务载体。

**Independent Test**: 预置一个有效租户、Agent 应用和本地通道绑定，提交一条包含
外部消息标识、用户标识、会话标识和文本的消息；无需其他用户故事即可验证收到成功
回复，并查询到相应的执行结果和审计记录。

**Acceptance Scenarios**:

1. **Given** 一个启用的租户、Agent 应用和匹配的本地通道绑定，**When** 绑定用户
   提交一条有效文本消息，**Then** 消息经过租户校验和 Agent 执行后返回非空统一回复。
2. **Given** 一条被成功处理的消息，**When** 平台返回回复，**Then** 回复包含该次
   请求的租户、会话、外部消息和链路关联信息，且不暴露内部凭据或敏感配置。
3. **Given** Agent 执行成功，**When** 操作人员按链路标识查询记录，**Then** 能找到
   一条结果为成功的审计记录并识别本次请求的关键处理阶段。

---

### User Story 2 - 保持会话连续且跨租户不串话 (Priority: P1)

作为平台租户，我希望自己的多轮会话保持上下文，同时任何其他租户都无法读取或影响
我的会话，使多个租户即使使用相同用户和会话标识也能安全共用平台。

**Why this priority**: 租户隔离是平台安全边界，也是 README 多租户目标和项目宪法的
强制不变量，必须与基本消息闭环同时成立。

**Independent Test**: 建立两个租户，并让它们使用相同的用户标识和外部会话标识交替
发送带有不同记忆标记的两轮消息；验证各租户第二轮只返回自己的第一轮标记。

**Acceptance Scenarios**:

1. **Given** 同一租户在同一绑定、用户和会话下已有一轮成功消息，**When** 该用户
   发送第二轮消息，**Then** Agent 能使用该租户本会话的先前上下文完成回复。
2. **Given** 两个租户使用相同用户标识和外部会话标识，**When** 两边交替发送消息，
   **Then** 每个租户只能获得自己的上下文，回复、会话状态和审计记录均不混用。
3. **Given** 内部 Gateway、Worker 或 Session Backend 边界收到租户 A 的可信上下文与
   租户 B 的 SessionIdentity 组合，**When** 组件尝试访问 SDK Session，**Then** 在
   SDK 调用前拒绝该错配，不返回另一租户的数据，也不修改任何会话。HTTP v1 不接受
   调用方提交 platform_session_id。

### User Story 3 - 安全处理重复投递 (Priority: P2)

作为通道集成方，我希望同一外部消息被重复或并发投递时只触发一次业务执行，使网络
重试不会产生重复回复、重复会话事件或重复业务动作。

**Why this priority**: IM 平台通常采用至少一次投递；没有幂等保护，后续接入真实 IM
时会放大费用、重复工具调用和数据一致性风险。

**Independent Test**: 对同一租户和通道绑定重复提交相同外部消息标识，包括一次顺序
重复和一次并发重复；验证只有一个首次业务执行结果，其余请求复用结果或收到明确的
处理中状态。

**Acceptance Scenarios**:

1. **Given** 一条消息已成功处理，**When** 相同租户、通道绑定和外部消息标识再次
   到达，**Then** 平台不再次执行 Agent，返回与首次相同的业务回复，并明确标记为
   重复投递结果。
2. **Given** 两个内容相同的首次请求并发到达，**When** 它们具有相同幂等作用域和
   外部消息标识，**Then** 最多一个请求获得业务执行权，且最终只产生一份业务结果。
3. **Given** 两个租户使用相同外部消息标识，**When** 两条消息分别到达，
   **Then** 它们被视为不同租户的独立消息，互不复用处理结果。
4. **Given** 相同租户和绑定复用了已有外部消息标识但消息内容不同，**When** 请求
   到达，**Then** 平台拒绝该冲突，不覆盖原结果，也不重新执行 Agent。
5. **Given** 同一租户会话的两条不同消息并发到达，**When** 两条消息都通过入口
   校验，**Then** 它们按获得会话处理权的顺序串行执行；其他会话不受该顺序阻塞。
6. **Given** 首次处理在 Agent 开始前失败，**When** 相同消息再次投递，
   **Then** 平台允许该消息重新竞争执行权。
7. **Given** Agent 已经开始执行且最终失败或结果不确定，**When** 相同消息再次
   投递，**Then** 平台不重新执行 Agent，并返回首次保存的失败或不确定结果。

### User Story 4 - 拒绝非法入口并追踪完整链路 (Priority: P2)

作为平台操作人员，我希望未知租户、无效通道绑定和处理失败都被默认拒绝并形成脱敏
审计，同时每次接收尝试都可以用一个链路标识追踪，使问题可定位且非法请求不会污染
会话数据。

**Why this priority**: 默认拒绝、审计和链路关联是安全演示以及后续监控、故障恢复的
基础，必须在接入真实外部通道前建立。

**Independent Test**: 分别提交未知租户、失效绑定、绑定不属于声明租户和 Agent
执行失败的请求；验证响应结果、无会话副作用、脱敏审计字段和链路标识一致性。

**Acceptance Scenarios**:

1. **Given** 请求无法解析到有效租户，**When** 消息到达，**Then** 平台在 Agent
   执行前拒绝请求，不创建或修改会话，并记录不泄露租户存在性的拒绝结果。
2. **Given** 通道绑定不存在、已停用或不属于已验证租户，**When** 消息到达，
   **Then** 平台在 Agent 执行前拒绝请求，不产生业务回复或会话写入。
3. **Given** 一条通过校验的消息，**When** 它经过入口、执行、状态读写、回复和
   审计阶段，**Then** 所有关联记录使用同一个链路标识。
4. **Given** Agent 执行失败，**When** 平台结束本次处理，**Then** 调用方收到明确
   的失败结果，审计记录包含可归类的错误信息，且秘密和完整消息正文不会写入审计。
5. **Given** 调用方使用有效绑定密钥对绑定标识、时间戳、外部消息标识和消息正文
   摘要签名，**When** 请求在允许的五分钟时钟偏差内到达，**Then** 平台验证签名
   后建立对应租户上下文。
6. **Given** 签名缺失、签名错误或请求时间戳超出五分钟时钟偏差，**When** 消息
   到达，**Then** 平台在租户数据访问和 Agent 执行前拒绝请求，并返回不泄露绑定
   是否存在的统一未授权结果。

### Edge Cases

- 同一个外部消息标识在不同租户或不同通道绑定下出现时，应分别处理。
- 已处理消息以相同标识但不同内容再次到达时，应视为幂等冲突并拒绝覆盖。
- 两个首次重复请求几乎同时到达时，最多允许一个请求启动 Agent 执行。
- 同一会话的不同消息并发到达时，应按获得会话处理权的顺序串行执行；不同会话可
  以并行处理。
- 缺少用户标识、会话标识、外部消息标识、通道绑定或消息正文时，应在执行前拒绝。
- 消息正文为空、仅含空白或超过 4000 个 Unicode 字符时，应返回可识别的输入错误。
- 租户或通道绑定在请求处理期间被停用时，不得为尚未取得执行权的请求开启执行。
- Agent 没有产生可用最终回复时，应记录失败，不得将中间事件伪装为成功回复。
- Agent 开始前失败不得永久占用执行权；Agent 开始后的失败或不确定结果必须作为
  幂等终态保存，防止相同消息自动重放。
- 审计记录写入失败时，不得把未经记录的业务执行报告为完全成功；失败必须对调用方
  和操作人员可见。
- 调用方提供链路标识时，非法格式不得污染日志；合法标识可以被继承，否则由平台
  生成新标识。
- HMAC 签名缺失、格式错误、验证失败或时间戳超出允许偏差时，应在访问租户业务
  数据前返回相同的未授权结果；允许时间窗内的重复消息继续受幂等规则约束。
- Channel Binding 改绑到另一个 Agent 时，后续消息必须生成新会话，不得把旧 Agent
  的上下文交给新 Agent。
- Worker 在进入 RUNNING 后超时或被取消时，应释放会话锁、保存 OUTCOME_UNKNOWN，
  并禁止相同消息标识自动重放；RUNNING 前的准备失败仍可重试。
- 本阶段幂等保证仅覆盖同一单进程生命周期；进程重启会清空状态，演示和文档不得
  将其描述为跨重启或生产级去重。

## Scope and Boundaries

### Included

- 一个可在本地启动和调用的文本消息入口。
- 两个预置租户、每个租户至少一个 Agent 应用和一个本地通道绑定。
- 统一入站消息、统一出站回复、租户上下文、会话身份、幂等记录和审计记录。
- 完整链路中的租户解析、绑定校验、幂等判断、会话路由、Agent 执行、回复和审计。
- 同租户多轮连续、跨租户隔离、重复投递和关键拒绝路径的自动化验收证据。
- 仅用于本地验证、可被后续共享后端替换的临时状态保存方式。

### Excluded

- 企业微信、微信客服、微信公众号、Telegram 等真实外部 IM 账号联调。
- Redis、SQL、向量库、对象存储或外部 Memory 服务。
- 多进程或多节点部署、跨节点共享状态、分布式锁及生产级高可用。
- Kubernetes、生产级容器编排、灰度发布和自动扩缩容。
- 真实模型供应商调用、模型 API 凭据和调用费用验证。
- 管理后台、租户自助注册、可视化配置和生产密钥管理系统。
- 图片、文件、卡片、流式回复、撤回和主动消息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 平台 MUST 接受一份统一的本地入站消息，至少包含通道类型、通道绑定
  标识、外部消息标识、外部用户标识、外部会话标识、会话类型和 1 至 4000 个
  Unicode 字符的非空文本内容。
- **FR-002**: 平台 MUST 在任何业务执行前，将入口携带的租户线索解析为经过验证的
  租户上下文；仅由调用方声明租户标识不得直接取得租户权限。
- **FR-003**: 平台 MUST 将有效通道绑定唯一解析到一个启用的租户和一个启用的
  Agent 应用，并拒绝不存在、停用或所有权不匹配的绑定。
- **FR-004**: 平台 MUST 默认拒绝未知租户、无效绑定和缺少必填字段的请求，且这些
  请求不得触发 Agent 执行或创建、读取、更新任何业务会话。
- **FR-005**: 平台 MUST 为每条通过校验的消息建立包含租户与 Agent 作用域的会话
  身份；两个租户或两个 Agent 即使外部用户和会话标识完全相同，也不得得到相同的
  平台会话身份。
- **FR-006**: 平台 MUST 让同一租户、Agent、绑定、用户和外部会话的后续消息继续
  使用原有会话上下文；绑定改绑 Agent 后必须建立新会话。
- **FR-007**: 平台 MUST 确保所有会话读取、写入、回复和审计均受已验证租户上下文
  约束，不得通过外部标识访问其他租户数据。
- **FR-008**: 平台 MUST 将通过校验且首次取得处理权的消息交给项目已经验证的上游
  Agent 执行能力，并以正式最终结果而非任意中间事件形成用户回复。
- **FR-009**: 平台 MUST 以租户、通道绑定和外部消息标识的组合识别重复投递，且
  幂等作用域不得跨租户共享。
- **FR-010**: 平台 MUST 保证同一幂等作用域内最多发生一次业务执行；顺序或并发的
  重复请求不得产生第二次 Agent 执行、第二份会话业务事件或第二次业务回复。
- **FR-011**: 平台 MUST 为已完成的重复请求返回首次执行结果；首次执行仍在进行时，
  MUST 返回明确且可重试的处理中结果，不得开启第二次执行。处理中结果关联当前
  owner attempt 的 trace，终态缓存结果关联实际启动 Agent 的 execution trace。
- **FR-012**: 平台 MUST 检测同一幂等标识对应不同消息内容的冲突，拒绝新请求并
  保留首次消息及其结果。
- **FR-013**: 平台 MUST 将成功结果转换为统一出站回复，至少关联租户、平台会话、
  外部消息、回复内容、处理状态和链路标识。
- **FR-014**: 平台 MUST 为每次入口接收创建或继承一个标准 UUID 格式的链路标识；
  调用方未提供或提供格式错误时必须生成新标识，并在校验、幂等、Agent 执行、会话
  访问、回复和审计记录中保持一致。幂等记录必须分别保存首次 claim、当前 owner
  attempt 和实际执行 Agent 的 trace，不能用首次 claim 冒充首次执行。
- **FR-015**: 平台 MUST 为成功、拒绝、重复、冲突和执行失败生成可查询的审计记录；
  认证后的查询必须显式使用租户作用域，并支持按租户、平台会话和 trace 查询。预认证
  拒绝记录只能通过受限的 system/pre-auth scope 访问。
- **FR-016**: 审计记录 MUST 至少表达租户、通道、用户、会话、Agent、处理决策、
  延迟、错误类型、成本信息和链路标识；当前阶段没有工具调用时可以不记录工具名称。
- **FR-017**: 审计和错误结果 MUST 对消息内容及标识进行最小披露，不得包含通道
  凭据、模型凭据、数据库密码或完整敏感正文。
- **FR-018**: 平台 MUST 对输入错误、权限拒绝、幂等冲突、处理中、执行失败和成功
  提供稳定且可区分的结果类别。
- **FR-019**: 平台 MUST 在审计无法可靠记录最终执行结果时显式报告链路不完整，
  不得把该请求标记为完全成功。
- **FR-020**: 本阶段所有业务状态 MUST 能在一次本地运行期间被保存和查询，并在
  进程重新启动后允许清空；不得把这种临时状态宣称为生产级持久化。
- **FR-021**: 租户、会话、幂等和审计状态 MUST 通过明确且可替换的数据访问边界
  管理，使后续更换共享后端时不改变上层业务语义。
- **FR-022**: 本阶段 MUST 在没有真实 IM 账号、真实模型凭据和外部模型调用的条件
  下完成全部验收。
- **FR-023**: 平台 MUST 串行处理同一租户作用域会话内的不同消息，并允许不同
  会话并行处理；会话顺序不得依赖某个固定 Worker 的进程身份。
- **FR-024**: 幂等记录 MUST 区分 Agent 执行开始前失败与开始后失败；开始前失败
  可以由相同消息重新竞争执行权，开始后失败或结果不确定必须成为不可自动重试的
  终态，并向重复调用方返回首次保存的结果。实现上的开始边界是：Worker 准备完成、
  幂等状态成功变为 RUNNING 后，首次请求官方 Runner Event 之前；RUNNING 后发生的
  超时或取消均按 OUTCOME_UNKNOWN 处理。
- **FR-025**: 每个本地通道绑定 MUST 具有独立的签名密钥引用；平台不得把明文密钥
  保存到业务配置、源码、审计、日志、链路记录或错误响应中。
- **FR-026**: 本地入站请求 MUST 使用绑定密钥对绑定标识、请求时间戳、外部消息
  标识和原始消息正文摘要生成 HMAC 签名；平台只有在签名验证成功后才能建立可信
  租户上下文。
- **FR-027**: 平台 MUST 拒绝缺失或错误签名以及超出五分钟时钟偏差的请求，并对
  未知绑定和错误签名返回不可区分的未授权结果；时间窗内的重复投递继续按照
  FR-009 至 FR-012 和 FR-024 处理。
- **FR-028**: 平台 MUST 通过租户作用域的可替换 MetricsRecorder 记录本地验收所需的
  请求量、错误量、关键阶段延迟、Agent 耗时、状态后端耗时、通道投递量、token 用量
  和租户成本；本阶段未发生的真实模型、工具和 IM 指标必须明确记为零或 not_applicable，
  不得伪造生产遥测。指标记录失败必须产生脱敏的 `metrics_incomplete` 运维事件，
  但不得改写已提交的幂等终态或改变认证拒绝响应。

### Key Entities

- **Tenant**: 平台中的隔离和归属边界；具有唯一租户标识、启用状态和应用归属。
- **Agent Application**: 租户选择用于处理消息的 Agent 配置；属于且只能属于一个
  租户，并具有唯一名称或标识及启用状态。
- **Channel Binding**: 外部消息入口与租户、Agent 应用之间的授权绑定；包含绑定
  标识、通道类型、所有者、目标 Agent、启用状态和签名密钥引用。
- **Verified Tenant Context**: 入口校验后形成的可信请求上下文；关联租户、绑定、
  Agent、用户、链路和请求身份，是后续访问的强制作用域。
- **Inbound Message**: 标准化后的入站文本消息；关联通道、绑定、外部消息、用户、
  会话类型、外部会话和消息内容。
- **Session Identity**: 在平台内唯一定位多轮会话的身份；必须包含租户和 Agent
  作用域，并关联绑定、用户和外部会话。
- **Idempotency Record**: 记录一条外部消息的处理所有权、内容指纹、状态和最终
  结果；其唯一性受租户和绑定共同约束。状态至少区分待执行、执行中、成功、执行前
  失败、执行后失败和结果不确定，其中只有执行前失败允许相同消息重新竞争执行权。
- **Execution Result**: Agent 处理消息后的正式业务结果；表达成功、失败或处理中状态，
  并关联平台会话和链路。
- **Outbound Reply**: 返回通道调用方的统一回复；关联原始消息、执行状态、可展示
  内容和链路标识。
- **Audit Record**: 对接收、拒绝、重复、冲突、执行和回复结果的不可混租户记录；
  支持按租户、会话和链路追踪，同时遵循脱敏要求。
- **Metric Snapshot**: MetricsRecorder 按租户或受限 pre-auth scope 聚合的本地指标
  快照；不保存正文、签名、秘密或完整外部身份。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在本地验收环境中，操作人员可在 5 分钟内从启动平台到完成一条有效
  消息的全链路演示，并获得非空回复和可关联审计记录。
- **SC-002**: 两个租户使用相同用户和外部会话标识交替执行至少 20 次双轮验证时，
  会话上下文泄漏次数为 0，错误归属的回复和审计记录均为 0。
- **SC-003**: 对同一消息执行至少 100 次顺序重复投递和 20 组并发重复投递时，每组
  业务执行次数均为 1，重复业务回复和重复会话业务事件均为 0。
- **SC-004**: 未知租户、无效绑定、跨租户绑定和缺少必填字段的验收用例 100% 在
  业务执行前被拒绝，且会话副作用为 0。
- **SC-005**: 成功、拒绝、重复、冲突和执行失败的验收样本中，100% 可通过同一个
  链路标识关联入口结果和审计记录。
- **SC-006**: 全部审计与错误输出的敏感信息检查中，通道凭据、模型凭据、数据库
  密码和完整敏感正文的泄漏数量为 0。
- **SC-007**: 本阶段所有验收场景可在无真实 IM 账号、无模型凭据、无外部模型调用
  的环境中重复执行，并获得确定的通过或失败结论。
- **SC-008**: 平台状态访问边界的替换性检查能够证明租户校验、幂等、会话和审计
  业务规则不依赖本地临时存储的专属数据表示。
- **SC-009**: 在成功、拒绝、重复和执行失败的自动化场景后，租户作用域指标快照能
  100% 对应请求结果，并包含非负的链路、Agent 和状态后端耗时；无真实模型、工具或
  IM 调用的指标明确为零或 not_applicable。

## Assumptions

- 本阶段的主要使用者是开发人员、评审人员和答辩演示人员，而非生产终端用户。
- 仓库预置两个非敏感演示租户、对应 Agent 应用和本地通道绑定；不提供租户创建
  或配置管理界面。
- 每个演示绑定的 HMAC 密钥通过运行环境注入，仓库仅保存不具备秘密值的引用名称。
- 本地调用方能够提供稳定的外部消息、用户和会话标识；缺失时请求按输入错误处理，
  平台不自动猜测这些身份。
- “同一会话”默认由已验证租户、Agent、通道绑定、外部用户、会话类型和外部会话
  共同确定；绑定改绑 Agent 会产生新会话。
- 本阶段仅处理 1 至 4000 个 Unicode 字符的非空文本。
- 对首次并发重复请求，允许重复调用方收到“处理中”结果并稍后重试；不要求本阶段
  阻塞等待首次执行完成。
- 审计记录保存业务必要字段和内容摘要，不保存完整消息正文；本地运行结束后可清空。
- 成本字段在无真实模型调用时记录为零或“未发生”，但字段仍保留以验证数据链路。
- 第一阶段的确定性 Agent 能力作为本阶段离线执行依赖，并继续遵守固定版本和无外部
  网络调用约束。

## Dependencies and Constraints

- 依赖第一阶段已经验收的 Agent、Runner、Event 和 Session 基线能力。
- 本阶段的本地消息入口属于可演示 Channel，不代表真实企业微信或其他 IM 已接入。
- 本阶段状态保存仅用于单进程验收；多节点一致性、持久化和迁移在后续共享存储功能
  中定义，同一消息跨进程重启后的去重不属于本阶段保证。
- 所有状态访问必须经过可替换边界，后续共享后端不得改变本规格定义的租户隔离、
  幂等和错误语义。
- 如果审计完整性与返回成功发生冲突，优先保证审计失败可见，不允许静默成功。
