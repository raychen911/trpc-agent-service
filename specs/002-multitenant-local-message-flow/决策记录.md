# 第二阶段决策记录：多租户本地消息闭环

**功能编号**：`002-multitenant-local-message-flow`
**记录日期**：2026-09-05
**状态**：持续更新

## 1. 记录目的

本文记录第二阶段从规格澄清到交付验收中的关键人为决策。它用于说明哪些风险由 AI
协助识别、有哪些可选方案、最终由人选择了什么、为什么这样选择，以及如何通过代码
和测试证明决定已经落实。

AI 在本流程中的职责是分析需求、暴露歧义、提出候选方案、说明取舍并检查一致性；
人负责理解业务和风险、作出最终判断、批准范围，并对实现与交付结果负责。

## 2. 决策方法

每个决定按以下顺序形成：

1. 从 README、项目宪法和当前规格识别可能影响安全、数据或验收的歧义。
2. 比较互斥方案对正确性、安全性、复杂度、后续扩展和测试的影响。
3. AI 给出建议及理由，但不替代项目负责人作出决定。
4. 人明确选择方案后，立即写回规格和本记录。
5. 在 plan、tasks、测试和 converge 中追踪决定是否真正落地。

## 3. 已确认决定

### D-001 同一会话并发顺序

- **问题**：同一租户会话的两条不同消息同时到达时如何处理？
- **候选方案**：串行执行；乐观并发冲突重试；并发执行并最后写入覆盖。
- **人的选择**：同一会话串行执行，不同会话可以并行。
- **判断依据**：多轮对话依赖确定顺序；最后写入覆盖会造成上下文不稳定，乐观重试
  对本地最小切片过重。按会话串行能够保留后续迁移到共享锁或版本控制的业务语义。
- **代价**：单个热点会话的吞吐量受顺序执行限制，但不同会话仍可并行。
- **验收证据**：同会话并发消息顺序测试、不同会话并行测试、跨租户隔离测试。
- **决策人**：项目负责人（用户）
- **AI 作用**：识别一致性风险、比较方案并推荐安全默认值。

### D-002 Agent 失败后的幂等重试

- **问题**：首次处理失败后，相同外部消息标识是否允许重新执行 Agent？
- **候选方案**：所有失败不可重试；所有失败均重试；区分 Agent 开始前与开始后。
- **人的选择**：Agent 开始前失败可重试；开始后失败或结果不确定不可自动重试。
- **判断依据**：开始前不存在业务副作用，可以安全释放执行权；开始后可能已有不可见
  副作用，自动重试会破坏“最多执行一次”。需要人工重试时必须使用新的外部消息标识。
- **代价**：部分暂时性执行失败不会自动恢复，但避免重复工具动作和重复回复。
- **验收证据**：开始前失败重试测试、开始后失败缓存测试、结果不确定不重放测试。
- **决策人**：项目负责人（用户）
- **AI 作用**：指出失败阶段与副作用边界，提出分阶段重试方案。

### D-003 本地通道绑定认证

- **问题**：本地 HTTP 调用方如何证明有权使用指定的通道绑定？
- **候选方案**：只校验绑定编号；固定访问令牌；HMAC 请求签名；仅信任本机。
- **人的选择**：每个绑定使用独立 HMAC 密钥，对请求内容和时间戳签名；只有验签成功
  才产生不可由请求 JSON 构造的 VerifiedBindingScope，用于解析 TenantContext。
- **判断依据**：调用方声明租户或绑定不构成可信身份；HMAC 同时验证来源与内容
  完整性，并与后续 IM 回调验签的安全模型一致。五分钟时间窗限制旧请求重放。
- **代价**：调用方需要统一签名规则和时钟同步，测试需要覆盖签名及时间边界。
- **验收证据**：有效签名、错误签名、未知绑定、超时请求、日志秘密扫描测试。
- **决策人**：项目负责人（用户）
- **AI 作用**：识别伪造租户风险，比较认证方案并说明与真实 IM 接入的衔接价值。

### D-004 审计与指标的租户作用域

- **问题**：记录中带有 tenant_id，是否足以阻止跨租户查询？认证前拒绝又如何记录？
- **候选方案**：只依赖记录字段过滤；所有操作强制 TenantScope；区分 TenantScope 与
  受限 PreAuthScope。
- **人的选择**：认证后的 append、update、query 和指标快照必须显式传入 TenantScope；
  认证前只允许 PreAuthScope，不能读取或修改租户记录。
- **判断依据**：字段过滤容易因漏写条件导致越权；把授权上下文纳入端口签名，能在
  Repository/Adapter 边界统一拒绝。指标只作可观测证据，写失败产生脱敏运维事件，
  不反向改写已提交业务终态或改变认证拒绝响应。
- **代价**：端口签名和测试 fixture 更明确、更繁琐，但后续替换 SQL/Redis 时仍可复用。
- **验收证据**：T006、T011、T012、T017、T049、T054、T057、SC-009。
- **决策人**：项目负责人（用户）
- **AI 作用**：指出“有 tenant_id 不等于已授权”，补充作用域端口和最小指标缺口。

### D-005 最终审计与幂等终态的提交顺序

- **问题**：如果先保存幂等终态、再写最终审计，而审计失败，终态不可变会留下无法修复
  的“业务成功但审计缺失”。
- **候选方案**：终态后审计；审计后终态；分布式事务。
- **人的选择**：幂等记录保持 RUNNING，先写最终审计，再条件提交 SUCCEEDED 或
  FAILED_POST_START；最终审计失败保存不可重放的 `audit_incomplete`，终态提交结果
  不确定保存 OUTCOME_UNKNOWN，终态后不再审计更新。
- **判断依据**：本阶段 InMemory 不引入分布式事务，但必须保证终态不可变与审计链闭合；
  先审计再 CAS 能消除“终态之后再失败”的非法转换。
- **代价**：已得到 Agent 结果时，最终审计故障仍会使对外结果失败，但不会自动重放潜在
  副作用。
- **验收证据**：T036、T037、T039、T041、T044、T046、T050、T055。
- **决策人**：项目负责人（用户）
- **AI 作用**：发现状态机与调用顺序冲突，给出可测试的故障顺序。

### D-006 Agent 开始、超时与取消边界

- **问题**：何时算 Agent 已开始，决定同一 external_message_id 是否可以重试。
- **候选方案**：调用 Worker 即开始；创建 Runner 即开始；准备完成后、首次请求 Runner
  Event 前进入 RUNNING。
- **人的选择**：Worker 先完成可失败准备；Gateway 随后写 RUNNING 和 execution_trace_id；
  紧接着、首次请求 Runner Event 前形成执行开始边界。本地默认超时 30 秒，RUNNING 后
  超时或取消进入 OUTCOME_UNKNOWN，并在 finally 释放 session lease。
- **判断依据**：准备错误没有 Agent 副作用，可安全 reclaim；开始后的超时/取消无法证明
  未产生副作用，不能自动重放。
- **代价**：不确定结果需要新消息标识或人工处理，换取最多执行一次的安全语义。
- **验收证据**：T016、T023、T036、T039、T044、T046、T050、T057。
- **决策人**：项目负责人（用户）
- **AI 作用**：把抽象的“调用过 Agent”细化为可实现、可故障注入的边界。

### D-007 Agent 是会话身份的一部分

- **问题**：同一 Binding 改绑到不同 Agent 后是否继续旧 Session；HTTP 是否允许调用方
  自带 platform_session_id 做跨租户测试？
- **候选方案**：会话只按 tenant/binding/user/conversation；加入 agent_id；接受外部
  platform_session_id。
- **人的选择**：SessionIdentity 包含 tenant_id、agent_id、binding、channel、外部用户
  和会话；改绑 Agent 生成新 Session。HTTP v1 不接受 platform_session_id，错配场景在
  Gateway/Worker/SessionBackend 内部契约测试中构造并在 SDK 调用前拒绝。
- **判断依据**：不同 Agent 的提示词、工具和状态语义不同；让调用方提供平台会话标识会
  扩大越权攻击面，也与公开请求契约冲突。
- **代价**：Agent 改绑后不保留旧上下文，但隔离语义稳定、接口更安全。
- **验收证据**：T006、T010、T027–T035、T060。
- **决策人**：项目负责人（用户）
- **AI 作用**：发现模型键、用户故事和 HTTP 契约不一致，提出内部边界测试方案。

### D-008 重复终态响应与 trace 语义

- **问题**：重复请求命中执行中或失败终态时返回什么；当前投递与原执行 trace 如何区分。
- **候选方案**：全部返回当前 trace；全部返回首次 trace；同时保存 current、owner、
  execution 三类 trace 并按状态选择。
- **人的选择**：每次投递均有 current trace；PENDING/RUNNING 返回当前 owner_trace_id；
  所有终态缓存返回 execution_trace_id 作为 original_trace_id。缓存成功返回正文；缓存
  FAILED_POST_START 保留 502，OUTCOME_UNKNOWN 保留 503，均为
  `delivery_action=suppress`、不可自动重放。
- **判断依据**：首次 claim 不一定是最终执行 owner；显式区分可以同时满足链路追踪、
  reclaim 和稳定 HTTP 语义。
- **代价**：幂等记录字段和响应测试更多，但避免重复回复与错误归因。
- **验收证据**：T036、T037、T041、T044–T046、T049、SC-008。
- **决策人**：项目负责人（用户）
- **AI 作用**：发现失败终态响应和 trace 来源未定义，统一状态—HTTP—审计语义。

## 5. 答辩表达要点

- 项目不是让 AI 自动生成代码后直接接受，而是把 AI 用作需求分析、风险发现、方案
  比较和一致性检查工具。
- 人保留对范围、安全边界、数据语义和验收结果的最终决定权。
- 每项重要决定都能从“问题 → 选项 → 人的判断 → 规格 → 计划 → 测试证据”追踪，
  体现 AI Native 开发中的人机责任分工。
- 最终评价标准不是生成了多少内容，而是决定是否可解释、实现是否符合决定、证据
  是否足以支持交付。
