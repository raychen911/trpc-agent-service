## DEC-001：策略变更立即生效

### 问题

租户管理员收紧或禁用治理策略后，多节点系统中的新请求及尚未执行的危险操作从何时开始遵守新策略？

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 立即生效，在新的治理判断和工具执行前校验当前有效版本 | 安全边界最明确，可阻止旧宽松策略继续授权 |
| B | 允许明确的短暂传播窗口 | 可减少读取压力，但窗口内仍可能按旧规则放行 |
| C | 下一次 Session 才生效 | 实现简单，但长会话可能长期保留旧权限 |

### 最终决定

选择方案 A。

- 策略收紧或禁用后，新的治理判断立即采用当前有效版本。
- Agent 已选择工具但工具尚未运行时，必须在执行前再次确认策略版本。
- 已经完成的外部副作用不由治理层自动回滚，而是通过审计保留其执行时采用的策略版本。
- 任何节点不得因为本地缓存仍存在旧版本而继续授权高风险操作。

### 判断逻辑

1. 工具权限和危险操作属于安全边界，不能接受长时间的最终一致窗口。
2. 多节点环境中“缓存仍可读取”不等于“缓存仍有授权效力”。
3. 在真正产生副作用前进行最终授权检查，可以覆盖 Agent 推理期间策略变化的竞态。
4. 不自动回滚已完成副作用，是为了避免治理系统在不了解外部业务补偿语义时制造二次风险。
5. 该决定符合项目宪法的默认拒绝和租户隔离原则。

### 对验收的影响

- 测试策略收紧后，所有节点的新请求都使用新版本。
- 测试工具已被选择但尚未运行时撤销权限，工具调用次数必须为 0。
- 测试旧缓存存在时仍不能放行已被禁用的工具。
- 审计必须记录实际采用的策略版本及拒绝原因。

## DEC-002：同时支持文本确认和结构化按钮

### 问题

飞书和企业微信中的危险操作，第一版应采用一次性确认编号文本回复、结构化按钮，还是同时支持两种方式？

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 仅支持一次性确认编号文本回复 | 跨渠道通用、实现最小，但用户需要手动输入 |
| B | 仅支持结构化按钮 | 体验直观，但渠道能力和回调格式差异较大 |
| C | 同时支持文本确认和结构化按钮 | 可兼顾通用性与体验，但增加契约、幂等和双渠道测试工作 |

### 最终决定

选择方案 C。

- 飞书和企业微信都提供一次性确认编号文本回复及最小结构化确认按钮。
- 两种交互不是两套授权流程，必须引用并消费同一份待确认事实。
- 待确认事实绑定原租户、渠道主体、Agent、Session、操作及参数摘要、策略版本和有效期。
- 任意一种方式成功确认后，另一种方式立即失效。
- 本决定只扩展危险操作确认所需的最小按钮，不将通用业务卡片、富文本或流式卡片纳入本阶段。

### 判断逻辑

1. 文本确认可作为所有渠道都能使用的可靠基线，也便于本地自动化测试。
2. 结构化按钮能减少用户输错编号，适合真实 IM 演示和答辩。
3. 两种方式共用待确认事实，可以避免重复授权和重复执行副作用。
4. 将按钮范围限定在危险操作确认，可控制用户选择 C 带来的范围扩张。
5. 身份、有效期和一次性消费比按钮或文本的表现形式更重要，两者必须服从相同安全语义。

### 对验收的影响

- 两种渠道分别验证文本确认与按钮确认。
- 先使用按钮、再重放文本编号时，工具总执行次数必须为 1；反向顺序同样成立。
- 其他用户、其他群成员、其他租户和过期确认均必须拒绝。
- 按钮回调缺失可信主体身份时必须默认拒绝。
- 自动化测试使用 SDK 替身完成，不要求真实危险工具产生副作用。

## DEC-003：按单次最大额度严格预占

### 问题

真实 Token 和成本通常在执行后才能确定，第一版预算控制应严格预占单次最大额度，还是按估算值预占并允许有限超额？

### 候选方案

| 方案 | 说明 | 主要影响 |
|------|------|----------|
| A | 按租户配置的单次最大额度严格预占 | 不突破预算，语义和测试清晰，但额度利用率较保守 |
| B | 按估算值预占并允许有限超额 | 利用率较高，但并发、恢复和成本归属更复杂 |
| C | 仅限制请求和工具次数，暂不限制 Token 与成本 | 工作量最小，但不能完整满足 README 要求 |

### 最终决定

选择方案 A。

- 请求只有在能够完整预占当前租户单次最大额度时才能进入受控执行。
- 执行完成后按实际用量结算，并释放未消费的预占部分。
- 执行前失败时释放全部预占；已经产生用量时必须完成一次且仅一次结算。
- 重复消息、渠道回复重试和恢复流程不得重复预占或重复结算。
- 实际执行必须受已预占上限约束，不允许因为估算偏差突破租户预算。

### 判断逻辑

1. 第一版首先证明预算边界不可突破，比追求额度利用率更重要。
2. 严格预占便于多节点使用单一原子准入语义，降低竞态和恢复复杂度。
3. 确定性 Runner 可稳定模拟最大额度、实际用量和剩余释放，验收证据清晰。
4. 代价是临界额度下可能提前拒绝实际成本较低的请求，但这是可解释的保守取舍。
5. 后续获得真实模型用量分布后，可以独立评审估算预占，不应在缺乏数据时提前放宽成本边界。

### 对验收的影响

- 至少 20 个跨节点并发请求竞争临界预算时，批准总量不得突破预算。
- 剩余额度小于单次最大额度时，即使预估实际用量较低也必须拒绝。
- 实际用量低于预占时，差额必须释放并可供后续请求使用。
- 节点在执行或结算期间中断后，恢复流程不得重复扣减。
- 所有预算决定必须关联 tenant_id、执行标识、策略版本和 trace。

## DEC-004：待确认危险操作的预算预占生命周期

### 问题

危险工具在首次治理判断时需要确认。如果确认在后续消息中到达，首次请求的严格预算预占应继续冻结、释放后重新预占，还是不产生预算事实？

### 最终决定

选择“单次预占、确认期间保持”。危险操作创建 PendingConfirmation 前，先按 DEC-003 原子预占该受控执行的四维单次最大额度；等待确认期间 reservation 保持 `RESERVED` 并与 confirmation/execution 绑定。确认成功后沿用同一 reservation，转为 `EXECUTING`/`SETTLED`，不得重新预占；确认过期、取消、策略收紧、身份或参数不匹配且尚未执行时，释放该 reservation。回复重试、重复确认和节点恢复只复用同一 reservation，不得重复占用或结算。

### 约束与理由

- 任何危险工具在没有可完整预占额度时都不得生成可执行确认事实。
- PendingConfirmation TTL 必须同时作为 reservation 保留上限；过期清理以原子方式将未执行 reservation 转为 `RELEASED`。
- 已进入 `EXECUTING` 的 reservation 不因确认回复失败或节点中断自动释放；无确定结果时进入 `REVIEW_REQUIRED`。
- 该语义避免“先确认后预占”造成预算竞态，也避免文本与按钮入口各自重新预占；代价是用户长期不确认会暂时占用额度，因此必须有有限 TTL 和可审计释放。

### 对验收的影响

- 等待确认期间账户必须满足 `settled + reserved <= hard_limit`，且 reservation 数量保持 1。
- 确认过期/取消后额度可被后续请求复用；确认成功后 actual 只结算一次。
- 文本→按钮、按钮→文本、重复投递和接管场景均断言不重复预占、不重复结算。

## 综合评审结论

ACA 形成的整体策略是：

1. 以立即失效和严格预占建立不可突破的权限、工具与成本边界。
2. 在安全状态唯一的前提下，同时提供文本和按钮两种确认入口，改善真实 IM 使用体验。
3. 所有节点、渠道和交互方式共享同一租户策略、待确认事实、预算事实、幂等语义与审计语义。
4. 选择 C 增加的结构化按钮工作量必须限制在危险操作确认，不扩展为通用卡片系统。
5. 后续若放宽策略传播或预算超额，必须作为新的决策重新评审，并补充并发、恢复和跨租户测试。

## 答辩说明建议

可以概括为：本阶段并非让 AI 自行决定安全规则，而是由人对策略即时性、用户体验和成本一致性进行取舍。最终选择在权限和预算上采取保守的强边界，同时允许双确认入口改善交互；AI 的作用是分析风险、检查决策之间是否矛盾，并把人的决定转化为可执行需求和验收证据。
