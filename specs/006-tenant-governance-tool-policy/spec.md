## User Scenarios & Testing *(mandatory)*

### User Story 1 - 租户策略隔离与默认拒绝 (Priority: P1)

作为平台管理员，我希望每个租户只能使用自己的治理策略，使某一租户的工具权限、用户授权、预算及敏感信息规则不会影响其他租户。

**Why this priority**: 治理策略属于租户安全边界；如果策略来源可伪造、失效时放行或跨租户读取，后续权限和成本控制都会失去意义。

**Independent Test**: 配置两个使用不同工具、预算和内容规则的租户，通过各自可信 Channel Binding 发送相同请求，验证每条请求只依据所属租户的有效策略做出决定。

**Acceptance Scenarios**:

1. **Given** 租户 A 允许某工具而租户 B 禁止该工具，**When** 两个租户发送相同请求，**Then** A 可进入后续执行，B 在工具运行前被拒绝。
2. **Given** 租户 A 已达到预算上限而租户 B 仍有额度，**When** 两个租户继续请求，**Then** 仅 A 被拒绝，B 不受影响。
3. **Given** 入站消息携带伪造 tenant_id、策略版本或权限声明，**When** 请求进入治理链路，**Then** 系统只接受可信 Channel Binding 确定的租户和服务端策略。
4. **Given** 租户、应用或治理策略未知、禁用、无有效版本或无法读取，**When** 请求到达，**Then** 系统默认拒绝，不得使用其他租户或隐式宽松策略代替。
5. **Given** 治理策略被收紧或禁用，**When** 任意节点开始新的治理判断或准备执行尚未运行的工具，**Then** 变更立即生效，节点必须校验当前有效版本并拒绝使用旧宽松策略；已经完成的副作用不回滚。

### User Story 2 - IM 用户身份授权 (Priority: P1)

作为租户管理员，我希望控制哪些飞书或企业微信用户可以使用指定 Agent，从而避免能够找到机器人但未获授权的用户访问租户能力。

**Why this priority**: Channel Binding 只能证明机器人属于哪个租户，不能自动证明发送者有权使用该租户的 Agent、工具和预算。

**Independent Test**: 在同一 Channel Binding 下分别使用已授权、未授权、已禁用、跨租户及身份缺失的测试主体发送消息，验证只有有效授权主体可以进入 Agent 执行。

**Acceptance Scenarios**:

1. **Given** 渠道主体已获得当前租户及 Agent 的有效权限，**When** 其发送受支持消息，**Then** 请求进入后续治理流程。
2. **Given** 渠道主体未授权、已禁用、授权过期或只属于其他租户，**When** 其发送消息，**Then** 系统在 Agent 执行前拒绝，并且不创建可继续使用的业务会话。
3. **Given** 群聊中机器人被明确 @，**When** 发送者已授权，**Then** 沿用既有群聊 Session 边界；发送者未授权时不得读取或写入该 Session。
4. **Given** 渠道未提供可验证的稳定发送者身份，**When** 消息到达，**Then** 系统不得用显示名、正文或调用方补充字段推断身份，并按默认拒绝处理。
5. **Given** 同一字符串形式的用户标识分别来自飞书和企业微信，**When** 系统查询授权，**Then** 两个主体保持独立，不发生授权串用。

### User Story 3 - 工具白名单与危险操作确认 (Priority: P1)

作为租户管理员，我希望只开放明确批准的工具，并要求具有明显副作用的危险操作再次确认，从而阻止 Agent 越权或因误解用户意图执行不可逆操作。

**Why this priority**: 工具能够连接企业数据和外部系统，错误调用的影响通常高于普通文本回复，必须在执行前形成强制安全门禁。

**Independent Test**: 使用无真实副作用的确定性工具替身，分别触发允许工具、禁止工具、危险工具未确认、有效确认、确认过期、参数变化和重复确认场景。

**Acceptance Scenarios**:

1. **Given** 工具未在当前租户白名单内，**When** Agent 申请调用，**Then** 工具代码不得运行，用户获得稳定且不泄露策略细节的拒绝结果。
2. **Given** 工具已允许但被标记为危险操作，**When** 尚无有效确认，**Then** 系统只生成待确认提示，不产生工具副作用。
3. **Given** 确认与原租户、渠道主体、Agent、Session、操作内容和有效策略完全匹配，**When** 用户提交确认，**Then** 对应工具最多执行一次。
4. **Given** 确认已过期、已使用、来自其他租户/主体/会话或操作参数已变化，**When** 用户提交确认，**Then** 系统默认拒绝且不执行工具。
5. **Given** 同一确认消息被重复投递或由多个节点同时处理，**When** 系统受理确认，**Then** 最多只有一个节点获得有效执行权，其余请求复用结果或得到稳定冲突结果。
6. **Given** 用户需要确认危险操作，**When** 平台发送确认提示，**Then** 飞书和企业微信同时提供一次性确认编号文本回复和结构化按钮；两种方式指向同一待确认事实，并且只能由原租户、原渠道主体和原 Session 使用一次。

### User Story 4 - 租户预算与调用配额 (Priority: P1)

作为租户管理员，我希望限制每个租户的请求、Token、工具调用和抽象成本用量，从而避免单个租户耗尽共享资源，并让成本归属可以解释。

**Why this priority**: 多租户共享执行资源时，单纯统计而不在执行前约束会造成资源争抢和不可控成本。

**Independent Test**: 为两个租户设置不同限额，使用用量可预测的 Agent 和工具替身发起并发请求，验证额度占用、完成结算、失败释放、重复消息和恢复流程。

**Acceptance Scenarios**:

1. **Given** 租户额度充足，**When** 一次受控调用开始，**Then** 系统先形成唯一额度占用，完成后按实际用量结算。
2. **Given** 多个并发请求合计超过预算或并发上限，**When** 不同节点同时检查，**Then** 只允许限额覆盖的请求继续，不得因并发读取而全部放行。
3. **Given** 调用在产生实际用量前失败，**When** 处理结束或恢复任务收敛，**Then** 未消费的占用被释放。
4. **Given** Agent 已产生用量但回复发送失败，**When** 渠道重试、重复投递或故障恢复发生，**Then** 不得重新执行 Agent 或重复结算相同用量。
5. **Given** 预算状态无法判定，**When** 请求需要消耗受控资源，**Then** 系统默认拒绝，不按无限额度处理。
6. **Given** 实际 Token 或成本只有执行完成后才能确定，**When** 调用开始，**Then** 系统按当前租户配置的单次最大额度严格预占；额度不足时拒绝，执行结束后按实际用量结算并释放剩余部分，批准用量不得突破租户预算。

### User Story 5 - 敏感信息保护 (Priority: P2)

作为租户管理员，我希望入站文本、工具参数、Agent 输出、渠道回复、日志和审计应用一致的敏感信息规则，从而降低个人信息与凭证泄露风险。

**Why this priority**: 平台连接真实 IM 与企业能力，敏感内容可能从任意入口进入并在错误、追踪或审计中被二次传播。

**Independent Test**: 使用仅用于测试的手机号、邮箱、访问令牌和 Secret 标记，验证允许、脱敏及拒绝规则，并扫描所有可观察输出和持久化事实。

**Acceptance Scenarios**:

1. **Given** 内容命中当前租户的脱敏规则，**When** 内容进入 Agent 或准备回复，**Then** 对应片段被替换为稳定占位符，并只记录规则类型而非原文。
2. **Given** 内容命中必须拒绝的凭证规则，**When** 请求或回复经过安全检查，**Then** 处理停止并返回安全错误，不继续传播该值。
3. **Given** 日志、指标或审计需要描述规则命中，**When** 记录事件，**Then** 只记录类别、规则、长度或不可逆摘要等必要信息。
4. **Given** 内容安全检查异常或无法确定是否安全，**When** 请求或回复到达该边界，**Then** 系统默认拒绝，不绕过检查。

### User Story 6 - 治理审计与可解释性 (Priority: P2)

作为开发、运维或答辩审查人员，我希望通过 trace_id 解释一次请求采用了哪个策略版本、经过哪些判断、消耗多少额度以及为何允许或拒绝。

**Why this priority**: 治理能力只有可追踪、可复核，才能证明权限和成本隔离真实发生，而不是仅停留在配置定义。

**Independent Test**: 执行允许、拒绝、预算不足、待确认、确认成功、重复消息和依赖故障场景，按租户及 trace 查询不可变审计证据。

**Acceptance Scenarios**:

1. **Given** 任意治理决定，**When** 处理结束，**Then** 审计能够标识租户、渠道、用户主体摘要、Session、Agent、策略版本、工具、决定、耗时、错误、成本及 trace。
2. **Given** 请求跨节点处理或发生接管，**When** 查询审计，**Then** 既有 trace_id、owner_trace_id 和 execution_trace_id 的含义保持一致。
3. **Given** 高风险操作无法可靠记录审计事实，**When** 系统准备执行，**Then** 操作默认拒绝；普通无副作用请求同样不得被错误记录为成功。
4. **Given** 同一消息或确认被重复投递，**When** 查询治理审计，**Then** 可以区分首次拥有者、等待者、缓存重放和实际执行，实际执行记录最多一份。

### Edge Cases

- 策略在请求处理中被禁用、收紧或升级。
- 两个节点同时申请最后一份预算。
- Agent 选择工具后、工具执行前策略发生变化。
- 用户确认危险操作时，参数、Session、授权或策略版本已经变化。
- 确认已消费，但渠道回复失败并再次收到相同确认消息。
- Agent 已产生用量，但节点在预算结算完成前中断。
- 入站内容允许，但 Agent 输出命中出站拒绝规则。
- 脱敏后的回复超过渠道长度限制。
- 用户授权被撤销，但某节点仍保留旧策略视图。
- 治理策略、授权、预算或审计能力仅部分可用。
- 群聊其他成员复制危险操作确认文本或尝试代替原用户确认。
- 相同用户标识、工具名称或确认编号出现在不同租户或渠道。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 从可信 Channel Binding 和服务端配置确定租户及 Agent 上下文，不得接受入站消息扩大权限。
- **FR-002**: 每个租户 MUST 拥有可独立启用、禁用和版本化的治理策略，至少包含用户授权、工具白名单、危险操作、敏感信息、预算和审计规则。
- **FR-003**: 未知、禁用、过期、跨租户或无法验证的策略与授权 MUST 默认拒绝。
- **FR-004**: 策略读取、用户授权、预算状态、待确认状态和治理审计 MUST 通过可替换的数据访问契约管理。
- **FR-005**: 策略缓存和共享状态 MUST 显式包含可信租户作用域。策略收紧或禁用后，新的治理判断以及工具执行前的最终授权检查 MUST 使用当前有效版本；失效宽松策略不得继续授权尚未执行的操作，已经完成的副作用不执行治理层回滚。
- **FR-006**: 系统 MUST 使用渠道类型和渠道提供的稳定用户身份建立主体，不得用显示名或正文作为授权依据。
- **FR-007**: 用户授权 MUST 支持租户范围，并允许进一步限制到 Agent Application 或 Channel Binding；多层授权同时存在时取权限交集。
- **FR-008**: 未授权、已禁用、授权过期或身份不完整的主体 MUST 在 Agent 执行前被拒绝。
- **FR-009**: 系统 MUST 在 Agent 执行前完成入站内容检查、用户授权和预算准入，并在工具执行前再次完成工具权限与确认检查。
- **FR-010**: 系统 MUST 在统一回复交给原 Channel Adapter 前完成出站内容检查。
- **FR-011**: 工具权限 MUST 默认拒绝，只有当前有效租户策略明确允许的工具才可运行。
- **FR-012**: 每个可调用工具 MUST 具有稳定标识、副作用类别、危险等级、确认要求和用量维度。
- **FR-013**: 危险操作确认 MUST 同时支持一次性确认编号文本回复和 IM 结构化按钮。两种入口 MUST 绑定并消费同一份包含租户、渠道主体、Agent、Session、操作摘要、参数摘要、策略版本、有效期和一次性标识的待确认事实，不得产生两套独立授权状态。
- **FR-014**: 待确认事实和确认凭据 MUST NOT 保存可恢复的 Secret 或完整敏感参数。
- **FR-015**: 相同危险操作的重复确认、跨节点并发确认或确认消息重放 MUST 保证工具最多执行一次。
- **FR-016**: 租户预算 MUST 至少覆盖请求次数、工具调用次数、Token 用量和抽象成本单位。
- **FR-017**: 每次受控执行 MUST 具有唯一预算占用，并在准入时按当前租户配置的单次最大额度严格预占；完成后按实际用量结算并释放未消费部分，状态至少可区分待执行、已结算和已释放。
- **FR-017a**: 需要确认的危险操作 MUST 在创建待确认事实前完成一次完整预算预占；等待确认期间保持 `RESERVED` 并绑定同一 confirmation/execution，确认成功沿用该预占，确认过期、取消或执行前策略/身份/参数失配时原子释放；任何文本/按钮重放、回复重试或恢复流程不得重新预占。
- **FR-018**: 多节点并发准入及实际用量估算误差 MUST NOT 让批准用量突破租户预算；剩余额度低于单次最大额度时必须拒绝新的受控执行。
- **FR-019**: 重复消息、回复重试及故障恢复 MUST NOT 重复扣减同一执行的实际用量。
- **FR-020**: 预算状态不可判定时 MUST 默认拒绝受控执行。
- **FR-021**: 敏感信息策略 MUST 至少支持“脱敏”和“拒绝”，并适用于入站内容、工具参数摘要、Agent 输出、渠道回复、日志和审计。
- **FR-022**: Bot/App Secret、访问令牌、模型密钥、数据库密码及匹配到的凭证 MUST NOT 出现在源码、Git、普通日志、trace、指标标签、错误详情或数据库明文字段中。
- **FR-023**: 治理失败 MUST 映射为稳定且不暴露内部策略或后端细节的错误语义；Channel Adapter 只负责转换为安全回复。
- **FR-024**: 每个允许、拒绝、待确认、确认、预算不足及治理故障决定 MUST 形成不可变审计事实并携带既有 trace 上下文。
- **FR-025**: 治理审计 MUST 至少包含 tenant_id、channel、主体摘要、session_id、agent_name、tool_name、decision、policy_version、latency、error_type、cost 和 trace_id。
- **FR-026**: 指标 MUST 能观察治理允许/拒绝数量、预算用量、工具耗时与错误，但默认标签不得包含租户、用户、Session、消息或 trace 等高基数或敏感标识。
- **FR-027**: Worker MUST 保持无业务状态，不得依赖 sticky session；恢复所需的策略版本、预算、确认和执行事实必须可由其他健康节点访问。
- **FR-028**: 节点中断后，其他节点 MUST 能安全接管未完成治理流程，且不得重新执行已完成的 Agent 或工具副作用。
- **FR-029**: 策略、身份、预算、内容检查或审计依赖暂时不可用时 MUST 产生明确的拒绝、可重试或恢复状态，不得绕过治理。
- **FR-030**: 新增治理数据访问契约 MUST 具有本地测试实现与共享状态实现的一致行为验证。
- **FR-031**: 自动化验证 MUST 使用确定性 Agent、工具和 Channel 测试替身，不依赖真实模型、真实危险工具或真实租户凭证。
- **FR-032**: 至少两个租户的端到端测试 MUST 证明策略、授权、预算、确认、Session、审计和成本相互隔离。
- **FR-033**: 第二、第三和第五阶段的统一入站、统一回复、幂等、Session、trace 和审计契约 MUST 保持兼容。
- **FR-034**: 平台 MUST 优先复用官方 tRPC-Agent 的 Filter、Runner 和 Tool 边界；平台只新增租户策略解析、授权、预算、确认、审计及 Adapter 编排能力。

### Key Entities *(include if feature involves data)*

- **Tenant Governance Policy**: 某租户在一个不可变版本下生效的用户、工具、内容、预算和审计规则集合。
- **Channel Principal**: 由渠道类型和稳定渠道用户身份构成的规范化主体，不包含可伪造显示名。
- **Principal Grant**: 某主体在租户范围内的授权，可进一步限定到 Agent Application 或 Channel Binding，并包含状态和有效期。
- **Tool Descriptor**: 工具的稳定标识、副作用类别、危险等级、确认要求和用量维度。
- **Policy Decision**: 一次规则评估产生的允许、拒绝或待确认结论，以及策略版本、规则标识和稳定原因。
- **Pending Confirmation**: 与原主体和操作绑定、具有有效期且只能消费一次的确认事实。
- **Budget Account**: 租户在某预算周期和用量维度下的限额、占用及已结算用量。
- **Budget Reservation**: 某次执行对应的唯一额度占用及其结算或释放状态。
- **Redaction Finding**: 敏感信息类别、规则、位置摘要和处置结果，不包含命中原文。
- **Governance Audit Event**: 与现有 Audit Log 关联的不可变治理决策和用量事实。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 两个租户采用相反工具和用户策略时，跨租户错误授权、策略串用、Session 串话和成本串账数量均为 0。
- **SC-002**: 未授权、未知、禁用、过期和身份不完整主体的测试请求 100% 在 Agent 或工具执行前被拒绝。
- **SC-003**: 对同一危险操作进行至少 10 次跨节点并发或重复确认时，产生副作用的工具执行次数不超过 1。
- **SC-004**: 至少 20 个并发请求竞争临界预算时，只有能够完整预占单次最大额度的请求获准执行，最终批准用量不突破租户预算，重复结算次数为 0。
- **SC-005**: 测试敏感信息在渠道回复、日志、trace、审计、错误报告和持久化扫描中的未脱敏原文命中数量为 0。
- **SC-006**: 允许、拒绝、待确认、确认成功、预算不足和依赖故障场景均能通过 trace 找到策略版本、稳定原因及唯一执行事实。
- **SC-007**: 治理依赖故障、节点中断及回复失败测试中，绕过治理的执行次数和已完成 Agent/工具的重复执行次数均为 0。
- **SC-008**: 不配置真实模型 API、真实危险工具或真实租户凭证，也能重复完成双租户治理端到端验收。
- **SC-009**: 第二、第三和第五阶段的自动化回归测试继续通过，既有真实 IM 文本会话行为保持兼容。
- **SC-010**: 每项治理拒绝都能向用户提供稳定、可理解且不泄露内部规则与敏感值的结果。

## Assumptions

- 第五阶段的可信 Channel Binding、双 IM 主体字段、tenant-scoped Session、共享幂等、租约、fencing、恢复、统一回复和 Audit Log 继续作为本阶段基线。
- 第一版治理文本消息和确定性工具替身，并仅为危险操作确认支持最小结构化按钮；通用图片、文件、语音、业务卡片和流式内容仍不在范围内。
- 用户授权默认从租户范围开始，并可被 Agent Application 与 Channel Binding 的更窄授权限制；不存在任何显式授权时默认拒绝。
- 治理判断所需事实无法可靠读取或写入时默认拒绝，不以宽松策略维持可用性。
- 高风险操作必须先形成可审计的授权和确认事实；普通请求失败也必须暴露为明确失败，不能伪装为成功。
- Token 与成本使用确定性用量替身验证语义，真实模型计量不属于本阶段。
- 管理后台、真实模型 API、真实外部副作用工具、向量库、Kubernetes 和完整生产 Telemetry 不属于本阶段。
