# Feature Specification: 生产可观测性与运维收敛

**Feature Branch**: `feature/luwenjie`

**Input**: 在前七阶段已经完成多租户消息闭环、共享状态、双真实 IM、治理以及数据后端语义的基础上，补齐端到端可观测性、运行健康、告警、灰度发布、租户级配置回滚、容量评估、部署拓扑、故障演练和最终交付证据，使平台能够被诊断、运营和答辩验证。

## 1. Feature Summary

本阶段面向平台运维人员、租户管理员、开发人员和验收人员，建立统一、可查询且不泄露租户数据的运行证据。每条来自飞书或企业微信的请求都能以同一关联标识串起 Channel Adapter、Gateway、Worker、官方 Runner、Tool、Session/Memory 数据访问、回复投递和审计；平台能够同时回答“发生了什么”“影响了哪个租户”“失败停在哪一步”“是否可以安全重试”。

本阶段还补齐生产化设计中尚未闭环的运维要求：依赖健康和就绪状态、可操作告警、租户级灰度与回滚、容量测量方法、最小可运行部署、生产推荐拓扑、故障演练以及风险清单。所有结论必须区分自动化验证、真实环境测量和设计建议，不得用本地结果冒充生产容量或高可用承诺。

### 1.1 README 验收项映射

- 补齐“治理、监控和安全”中的请求量、错误率、关键链路延迟、模型与工具耗时、IM 投递、Token、成本和状态后端延迟。
- 补齐从 IM callback 到 Runner、Tool、Session/Memory 和 IM 回复的完整关联链路。
- 补齐“故障恢复与运维”中的节点与依赖故障诊断、灰度发布、租户级配置回滚和容量评估。
- 补齐最小可运行部署、生产推荐部署、最终架构说明、风险与验收证据。

### 1.2 Included

- 飞书、企业微信及现有 HTTP 测试入口的统一追踪、日志、指标和运行事件语义。
- Gateway、Worker、Runner、Tool、共享状态、数据访问、回复投递和恢复路径的端到端关联。
- 多租户可观测数据隔离、脱敏、低基数标签和受控查询。
- 健康、就绪、降级、依赖故障、告警与恢复确认。
- 租户级配置版本、灰度范围、推进条件、失败暂停和安全回滚。
- 可重复的容量场景、测量维度、结果边界和资源估算方法。
- 本地最小部署验收与生产推荐拓扑文档。
- 故障演练、风险登记和前七阶段回归证据汇总。

### 1.3 Excluded

- 真实模型 API、真实 Token 计费结算和真实外部副作用工具。
- 管理后台、可视化 Dashboard 产品和租户自助运维门户。
- 真实 Kubernetes 集群、自动扩缩容控制器、跨地域容灾和生产值班平台。
- 绑定某一商业监控、日志或告警供应商的专属实现。
- 修改飞书、企业微信或 tRPC-Agent 官方 SDK 源码。
- 对本地压测结果作生产 SLA、最大容量或成本承诺。

## Clarifications

### Session 2026-09-10

- Q: 对成功请求和异常请求，应采用哪种追踪采样策略？ → A: 错误、安全拒绝、恢复、跨租户尝试和结果未知请求 100% 保留完整诊断轨迹；普通成功请求按平台默认比例采样，租户只能在平台设定的安全上限内调整比例。
- Q: 普通遥测出口不可用或缓冲耗尽时，业务处理和待发送诊断数据应如何处置？ → A: 普通遥测故障不阻断业务；使用有界内存缓冲和有限重试，溢出时优先丢弃普通成功数据，关键异常保留最小脱敏摘要，并显式记录丢弃数量；正式 Audit 的既有 fail-closed 边界不变。
- Q: 当不同组件依赖发生故障时，节点和平台整体应如何判定 ready、degraded 与 unready？ → A: 使用角色级就绪矩阵；实例缺少自身安全处理所需的关键依赖时必须 unready，平台按仍可用的业务路径汇总状态；单一渠道或普通遥测故障只使受影响路径或平台 degraded，其他安全路径继续服务。
- Q: 灰度发布触发异常时，应采用怎样的自动暂停和配置回滚边界？ → A: 使用分级门槛；租户隔离、未授权副作用、数据一致性和配置不兼容是零容忍硬门槛，首次命中即自动停止灰度并让新请求切回已知良好版本；错误率、延迟等质量门槛按发布版本配置，越线只自动暂停并由授权人员确认是否回滚。
- Q: 本地 100 并发 Session、1,000 条消息的容量场景，应采用什么验收口径？ → A: 使用双层口径；业务结果零丢失、零跨租户串用和零不可解释重复是正确性硬门禁，可观测性相对同机基线的吞吐下降或分位延迟增幅不超过 10% 是性能回归门禁，不设置生产级绝对吞吐或延迟承诺。

## 2. User Scenarios & Testing

### US1 - 端到端链路诊断（Priority: P1）

作为平台运维人员，我希望从任意一条 IM 消息的关联标识看到完整处理轨迹，从而快速判断请求经过了哪些组件、在哪一步成功或失败，以及是否已经向原会话回复。

**Why this priority**: 如果链路跨组件后失去关联，已有幂等、恢复、治理和数据一致性能力就无法在真实故障中被解释和证明。

**Independent Test**: 分别从飞书、企业微信和测试入口发送成功、拒绝与失败请求，按关联标识查询完整阶段记录，并核对回复、审计与处理终态。

**Acceptance Scenarios**:

1. **Given** 一个已启用且绑定正确的机器人，**When** 用户发送文本消息并收到回复，**Then** 同一关联标识能够串起入口、租户绑定、幂等、Session、Worker、Runner、数据访问、回复投递和审计。
2. **Given** 请求在权限检查、工具确认、状态存储或 IM 发送阶段失败，**When** 运维人员查询关联标识，**Then** 能看到最后确认阶段、稳定错误类型、重试资格和最终状态，且不会显示 Secret 或消息原文。
3. **Given** 相同外部消息被重复投递，**When** 两个节点处理该消息，**Then** 轨迹能够区分首次执行与幂等命中，但只关联一个业务终态和一次不可重复副作用。

### US2 - 安全的租户级指标与日志（Priority: P1）

作为平台和安全管理员，我希望观察请求量、错误率、延迟、投递、用量和后端状态，同时保证不同租户的数据不可串查、指标标签不会造成无限增长、日志不会泄露身份或内容。

**Why this priority**: 可观测性本身会汇聚大量运行数据；若隔离和脱敏不足，它会成为新的跨租户泄露面。

**Independent Test**: 让两个租户使用相同用户、Session 和消息标识产生不同结果，验证查询结果隔离、敏感标记零命中且标签值集合有明确上限。

**Acceptance Scenarios**:

1. **Given** 两个租户产生同名会话与相同外部消息标识，**When** 分租户查询日志、指标和审计，**Then** 只能看到被授权租户的数据且聚合结果互不串用。
2. **Given** 消息正文包含手机号、邮箱、Token、Secret 或 response URL，**When** 请求经过成功与失败路径，**Then** 普通日志、指标、追踪、错误详情和运行事件中均不出现原值。
3. **Given** 大量不同用户、Session、消息和关联标识，**When** 汇总指标，**Then** 这些高基数原值不作为指标标签，平台仍能通过受控诊断入口定位单次请求。

---

### US3 - 健康、告警与依赖故障处置（Priority: P1）

作为值班人员，我希望明确区分进程存活、业务就绪和部分能力降级，并在 Redis、PostgreSQL、IM 长连接、回复发送或遥测出口异常时收到可操作且不会重复轰炸的告警。

**Why this priority**: 仅有进程存活无法说明请求是否能够安全处理；模糊健康状态会让流量进入不可用节点并扩大故障。

**Independent Test**: 依次注入关键依赖断连、认证失败、超时、恢复和重复抖动，验证就绪变化、业务语义、告警合并及恢复通知。

**Acceptance Scenarios**:

1. **Given** 进程仍运行但权威配置或状态后端不可用，**When** 健康状态被查询，**Then** 存活状态仍可用、业务就绪明确失败，受影响请求默认拒绝且原因可诊断。
2. **Given** 单个 IM 渠道断线而核心服务与另一渠道正常，**When** 状态被查询，**Then** 平台报告渠道级降级，不把全平台误报为不可用。
3. **Given** 同一依赖持续抖动，**When** 多次触发相同故障，**Then** 告警被去重或聚合；恢复稳定后产生一次明确恢复事件。

### US4 - 租户级灰度发布与配置回滚（Priority: P1）

作为租户管理员和发布负责人，我希望新 Agent 配置、治理策略或数据后端配置先对受控租户范围生效，只有满足验证条件才扩大范围；出现错误时可以恢复到最后一个已知良好版本。

**Why this priority**: 多租户共享平台不能用全量发布验证单个租户配置，错误配置也不能通过修改进程内状态临时掩盖。

**Independent Test**: 创建旧版本、新版本和两个租户灰度范围，验证范围外租户保持旧版本、失败后停止推进、回滚后新请求使用旧版本且历史审计不被改写。

**Acceptance Scenarios**:

1. **Given** 一个待发布配置版本和明确租户范围，**When** 启动灰度，**Then** 只有目标租户的新请求使用新版本，其他租户继续使用原版本。
2. **Given** 灰度期间首次出现跨租户、未授权副作用、数据一致性破坏或配置不兼容，**When** 平台评估硬门槛，**Then** 自动停止灰度并让目标租户的新请求切回已知良好版本。
3. **Given** 错误率、延迟或其他版本化质量门槛越线，**When** 达到该门槛要求的观察窗口或最小样本，**Then** 自动暂停推进并由授权人员决定继续或回滚。
4. **Given** 发布负责人回滚到已知良好版本，**When** 新请求到达任意健康节点，**Then** 所有目标租户都使用回滚版本；在途请求不混用配置，未执行副作用仍需通过当前安全检查，已完成副作用与历史审计不被反向修改。
5. **Given** 两个节点短暂运行不同软件版本，**When** 它们读取同一配置发布状态，**Then** 不支持该配置语义的节点不得宣称就绪或静默按旧宽松规则处理。

### US5 - 可重复的容量评估（Priority: P2）

作为架构师和运维人员，我希望使用固定业务画像测量并发 Session、消息吞吐、延迟、错误、共享后端压力和资源使用，从而估算部署规模并清楚说明结论适用范围。

**Why this priority**: 没有可重复工作负载和测量边界，节点数、后端容量与成本只能依赖猜测。

**Independent Test**: 在相同环境使用固定租户、会话、消息大小与并发梯度重复运行，比较结果差异并生成包含环境、负载、分位延迟、错误率和资源峰值的报告。

**Acceptance Scenarios**:

1. **Given** 一组固定负载参数，**When** 连续运行两次容量场景，**Then** 两次报告具有相同字段、明确环境信息和可解释差异。
2. **Given** 某项资源或依赖达到瓶颈，**When** 错误率或延迟明显上升，**Then** 报告能定位受限组件并停止把更高负载结果描述为可支持容量。
3. **Given** 测试只使用本地确定性 Runner，**When** 输出容量结论，**Then** 明确排除真实模型网络延迟、真实 IM 限流和生产基础设施 SLA。

---

### US6 - 最小部署与安全停机（Priority: P2）

作为开发和演示人员，我希望通过一套明确步骤启动至少两个 Worker、共享后端和现有渠道入口，并能在节点维护或退出时停止接收新请求、完成或移交在途任务。

**Why this priority**: 可运行拓扑和安全停机是证明“节点化”而非多个孤立进程的必要条件。

**Independent Test**: 从干净环境启动最小拓扑，完成跨节点消息，然后依次停止一个 Worker、渠道 Adapter 和共享依赖，验证排空、接管、状态与恢复说明。

**Acceptance Scenarios**:

1. **Given** 干净环境和通过安全方式注入的配置，**When** 按 Quickstart 启动，**Then** 所有必需组件达到明确就绪状态且两个节点可接续同一租户会话。
2. **Given** 一个 Worker 收到终止信号，**When** 开始停机，**Then** 它先退出就绪、停止接收新任务，并在限定时间内完成或安全移交在途工作。
3. **Given** 节点在排空前异常退出，**When** 租约到期并由新节点接管，**Then** 复用既有 fencing 和恢复机制，不产生重复业务结果。

### US7 - 生产推荐拓扑与故障演练（Priority: P2）

作为评审人员，我希望看到不绑定特定云厂商的生产推荐部署、故障域、恢复目标、灰度路径和至少八项主要风险，使设计足以指导后续工程落地。

**Why this priority**: 本课题以架构设计为主，必须明确本地演示与生产建议之间的差距和补齐路径。

**Independent Test**: 按拓扑和故障矩阵逐项走查节点、网络、数据库、缓存、渠道、配置、遥测和密钥故障，确认每项都有检测、影响、处置、恢复和证据责任人。

**Acceptance Scenarios**:

1. **Given** 最小部署和生产推荐部署，**When** 评审组件职责与数据流，**Then** Gateway、Worker、Channel Adapter、Storage Adapter、治理、Telemetry、数据库和 IM 平台名称与前七阶段一致。
2. **Given** 风险登记表，**When** 逐项评审，**Then** 至少八项生产风险均包含触发条件、影响、检测信号、缓解措施、恢复验证和剩余风险。
3. **Given** 一次故障演练，**When** 服务恢复，**Then** 运维人员能够用健康、追踪、指标和审计证明没有跨租户数据泄露或不可解释的重复副作用。

### US8 - 最终交付与验收追踪（Priority: P2）

作为导师或验收人员，我希望从 README 的每项要求追溯到规格、架构、代码、测试和真实/模拟证据，从而判断哪些已经完成、哪些只是设计、哪些仍依赖外部环境。

**Why this priority**: 清晰的证据边界能够防止把替身测试、本地压测或设计图错误表述为生产验证。

**Independent Test**: 随机选择 README 验收项并沿追踪表找到对应产物、命令和结果，核对范围声明与实际证据一致。

**Acceptance Scenarios**:

1. **Given** 任一 README 总体验收项，**When** 查阅追踪矩阵，**Then** 能定位对应阶段、需求、测试、演示步骤和证据状态。
2. **Given** 使用 SDK 替身或本地基础设施的验证，**When** 查看阶段成果，**Then** 文档明确标记验证环境与未证明的生产属性。
3. **Given** 前七阶段回归出现失败或跳过，**When** 第八阶段收敛，**Then** 不得宣称最终完成，必须记录失败原因、影响和补测条件。

### Edge Cases

- 上游未提供关联标识、提供格式错误标识或试图用消息正文覆盖平台标识。
- 同一请求跨节点接管后产生多个阶段记录，但只有一个权威业务终态。
- Telemetry 接收端变慢、断连、拒绝批次或恢复时，缓冲达到上限；平台必须优先丢弃普通成功数据并保留关键异常的最小脱敏摘要。
- 审计后端和普通遥测后端同时故障，两者的业务阻断语义不能混淆。
- 飞书或企业微信反复断线、认证失败、限流或返回结果未知。
- 租户被禁用、配置版本在灰度中被再次修改、回滚目标已失效或不兼容。
- 发布期间新旧节点对配置字段、错误类型或指标版本理解不一致。
- 低流量租户的百分比灰度无法形成有效样本。
- 高基数输入、超长错误、异常 Unicode 或恶意内容进入日志与标签边界。
- 容量测试中客户端先成为瓶颈，导致错误归因到服务端。
- 节点收到停机信号后仍持有租约、正在发送回复或处理结果未知的工具调用。
- 系统时钟偏移导致事件排序、延迟统计或告警窗口异常。

## 3. Requirements

### 3.1 Functional Requirements

- **FR-001**: 平台 MUST 为每个外部请求创建或接受一个符合平台规则的唯一关联标识；外部提供的值不符合规则时 MUST 重新生成，消息正文和不可信 metadata 不得覆盖该标识。
- **FR-002**: 关联标识 MUST 贯穿 Channel Adapter、Gateway、Channel Binding、幂等、Session、Worker、官方 Runner、治理、Tool、数据访问、回复投递、恢复和 Audit Log；不适用阶段必须明确标记而不能伪造成已执行。
- **FR-003**: 每个阶段记录 MUST 至少说明阶段名称、开始与结束时间、结果、稳定错误类型、节点角色、重试资格和上游/下游关系。
- **FR-004**: 节点接管、幂等命中、缓存回复、冲突拒绝和恢复补齐 MUST 与原始处理轨迹关联，同时保持各自执行标识可区分。
- **FR-005**: 平台 MUST 提供请求量、成功/拒绝/失败量、关键链路延迟、Runner 与 Tool 耗时、IM 接收与投递、Token 与抽象成本、Session/Memory/数据后端延迟及恢复结果的指标。
- **FR-006**: 指标定义 MUST 使用有界枚举标签；tenant、user、session、message、trace、正文、URL、异常文本和对象引用的原值不得作为指标标签。
- **FR-007**: 结构化日志、追踪、指标、运行事件和正式审计 MUST 使用一致的组件、阶段、结果和错误分类，且明确区分不可变审计事实与可丢弃运行诊断。
- **FR-008**: 错误、安全拒绝、恢复、跨租户尝试和结果未知请求 MUST 100% 保留完整诊断轨迹；普通成功请求 MUST 按平台默认比例采样，租户只能在平台设定的安全上限内调整比例，且不得降低关键异常的保留率。
- **FR-009**: 普通遥测出口不可用时，业务处理 MUST 继续遵守原有业务结果，不得阻塞或把遥测发送失败伪装成业务失败；待发送数据只能进入有界内存缓冲并执行有限重试，不得为此落盘原文。缓冲溢出时 MUST 优先丢弃普通成功数据，为关键异常保留最小脱敏摘要，并显式记录分类丢弃数量。
- **FR-010**: 正式 Audit Log 不可用时，平台 MUST 继续遵守第六、七阶段已确定的 fail-closed 边界；普通运行事件不得冒充、补写或替代正式审计。
- **FR-011**: IM 回复 MUST 记录排队、尝试、成功、明确失败、限流和结果未知状态；重试必须复用既有投递幂等语义。
- **FR-012**: 平台 MUST 分别报告进程存活、实例角色就绪、渠道连接、关键依赖和平台汇总状态；汇总状态 MUST 基于仍可安全完成的业务路径，不得用单一“健康”值掩盖局部降级或权威后端不可用。
- **FR-013**: 每类实例 MUST 按角色级就绪矩阵判断关键依赖：入口角色需要可信配置、Channel Binding 与幂等状态，执行角色需要可信配置、共享 Session/数据状态、租约/fencing、治理/Audit 边界和 Runner，渠道角色需要有效认证、对应连接与可达入口。实例缺少自身任一关键依赖时 MUST `unready`；普通遥测出口不是业务就绪的关键依赖。
- **FR-014**: 告警 MUST 包含影响范围、首次发生时间、当前状态、稳定原因、关联证据和建议操作；不得包含租户原始标识、用户内容或 Secret。
- **FR-015**: 相同原因和影响范围内的重复告警 MUST 合并或抑制；恢复达到稳定条件后 MUST 产生一次恢复通知并关闭活动告警。
- **FR-016**: 平台 MUST 允许按授权租户范围、时间窗口、组件、结果和关联标识查询诊断数据；查询本身必须经过授权并形成最小审计记录。
- **FR-017**: 租户可发布的 Agent、治理与数据后端配置 MUST 具有不可变版本、状态、创建者摘要、适用范围、兼容边界和变更摘要。
- **FR-018**: 灰度发布 MUST 明确目标租户集合、开始条件、观察窗口、最小样本、推进条件、暂停条件和完成条件；范围外租户不得提前读取新版本。错误率、延迟等质量门槛 MUST 作为不可变发布版本的一部分记录，未达到最小样本时不得仅凭低流量静默推进。
- **FR-019**: 跨租户访问、未授权副作用、数据一致性破坏和配置不兼容 MUST 作为零容忍硬门槛，首次命中即自动停止灰度并将目标租户的新请求切回已知良好版本。版本化质量门槛越线时 MUST 自动暂停扩大范围、保留当前证据，并由授权人员决定继续或回滚。
- **FR-020**: 回滚 MUST 将目标租户的新请求切回最后一个兼容且已知良好的配置版本；在途请求不得中途混用两个配置版本，尚未执行的副作用必须重新通过当前治理与安全检查，无法证明安全时进入既有拒绝或恢复路径。回滚不得删除或改写已经完成的业务副作用、预算事实、数据事件和审计记录。
- **FR-021**: 配置缺失、禁用、签名/摘要不一致、版本过旧、语义不兼容或状态不可判定时 MUST 默认拒绝，而不是回退到进程内默认配置。
- **FR-022**: 混合版本节点 MUST 声明其支持的配置和契约版本；不能安全解释当前权威版本的节点必须退出就绪。
- **FR-023**: 平台 MUST 定义可重复的容量场景，至少包含租户数、并发 Session、每 Session 消息数、消息大小、重复比例、工具比例、数据读写比例和节点数；正式本地门禁 MUST 覆盖 2 个租户、2 个 Worker、100 个并发 Session 和 1,000 条消息。
- **FR-024**: 每次容量运行 MUST 记录测试环境、配置版本、持续时间、成功/拒绝/错误数量、吞吐、分位延迟、关键依赖压力、资源峰值和瓶颈判断。业务结果丢失、跨租户串用或不可解释重复中的任一项非零时，正确性门禁 MUST 失败。
- **FR-025**: 容量验收 MUST 使用同一机器、同一配置和同一确定性工作负载建立关闭完整可观测性时的基线，再启用完整可观测性执行对比；吞吐下降或分位延迟增幅超过 10% 时性能回归门禁 MUST 失败。报告 MUST 区分已测量事实、推算结果和未覆盖因素，不得设置或暗示生产级绝对吞吐、延迟或 SLA。
- **FR-026**: 最小可运行部署 MUST 包含至少两个可替换 Worker、现有 Gateway/Channel 入口、共享配置与状态、统一审计和可观测出口，并提供从干净环境启动、验证和停止的步骤。
- **FR-027**: 生产推荐部署 MUST 说明组件副本、故障域、入口路由、共享数据权威、密钥来源、Telemetry 汇聚、发布顺序、备份恢复和扩缩容信号，但本阶段不要求部署真实生产集群。
- **FR-028**: 计划停机 MUST 先撤销就绪并停止接收新工作，再在限定时间内完成、移交或标记在途处理；非幂等未知结果不得自动重放。
- **FR-029**: 故障演练 MUST 覆盖节点、共享配置、状态后端、审计后端、IM 连接与发送、遥测出口、灰度配置和时钟异常，并验证恢复后业务与租户隔离不变量。
- **FR-030**: 风险登记 MUST 至少包含八项生产风险，每项记录触发条件、影响范围、检测信号、预防措施、处置步骤、恢复验证和剩余风险。
- **FR-031**: Secret、数据库凭证、IM 凭证、response URL、原始消息、用户身份和完整对象引用不得进入源码、Git、普通日志、追踪属性、指标标签、错误详情或告警正文。
- **FR-032**: 所有可观测记录 MUST 携带可信租户作用域或明确的平台级作用域；租户查询和聚合不得依赖调用者传入的未验证 tenant_id。
- **FR-033**: 平台 MUST 提供不依赖真实商业监控服务的测试替身和契约测试，验证追踪传播、指标标签、日志脱敏、健康状态、告警、灰度和回滚语义。
- **FR-034**: 集成与端到端测试 MUST 覆盖双 IM、双租户、双节点、成功/拒绝/故障、接管、遥测出口中断和配置回滚，并复用前七阶段幂等、fencing、恢复与审计机制。
- **FR-035**: 第八阶段验收 MUST 运行前七阶段回归，并分别记录通过、失败、跳过及外部环境原因；存在未解释失败时不得声明本阶段完成。
- **FR-036**: README、架构说明、数据流、部署拓扑、容量报告、风险清单、Quickstart 和验收记录 MUST 使用一致的组件名称和状态语义，并能追溯到对应需求与证据。

### 3.2 Non-Functional Requirements

- **NFR-001 性能开销**: 在相同机器、配置和确定性负载下，启用完整可观测性后的业务吞吐下降与端到端分位延迟增幅都不得超过 10%；任一超出即判定性能回归门禁失败，并记录瓶颈与整改证据。
- **NFR-002 诊断完整性**: 自动化验收中，所有已接受请求都必须拥有可查询的关联摘要；关键异常请求的完整诊断轨迹保留率为 100%，阶段缺口数量为 0。
- **NFR-003 隔离与保密**: 跨租户诊断数据返回数量为 0；预置敏感标记在日志、追踪、指标、告警和提交文件中的原文命中为 0。
- **NFR-004 可用性边界**: 普通遥测出口故障不得创建无限缓冲、阻塞全局消息循环或改变已经提交的业务终态；有界缓冲、有限重试、按优先级丢弃和分类丢弃数量必须可验证，正式 Audit 的 fail-closed 边界不得因此改变。
- **NFR-005 可移植性**: 观测、告警和部署设计必须保持供应商中立，并可映射到标准化分布式追踪与指标生态。
- **NFR-006 可重复性**: 基线与启用可观测性的容量场景必须使用相同负载定义；连续运行的关键统计字段必须完整，差异超过既定容差时必须给出环境或瓶颈解释后才能形成有效结论。
- **NFR-007 可维护性**: 新增错误、阶段、指标和配置状态必须通过集中定义扩展，不得在各 Adapter 中产生互相矛盾的命名。

### 3.3 Key Entities

- **Trace Context**: 一次外部请求及其派生执行的可信关联上下文，包含平台生成标识、租户作用域摘要、父子关系和采样决定。
- **Stage Observation**: 某组件处理阶段的开始、结束、结果、耗时、错误分类、节点角色和重试资格，不保存消息原文。
- **Metric Definition**: 指标名称、含义、单位、允许标签集合、结果枚举和基数上限。
- **Operational Event**: 可丢弃但可诊断的运行事实，与正式不可变 Audit Log 明确分离。
- **Service Health**: 组件或依赖的存活、就绪、降级、不可用状态及原因、首次发生与最近确认时间。
- **Alert Incident**: 由一个或多个健康/指标信号聚合的活动事件，包含影响范围、状态、证据引用和恢复条件。
- **Configuration Release**: 不可变配置版本及其兼容性、目标租户、灰度阶段、门槛、当前状态和回滚目标。
- **Capacity Scenario**: 固定工作负载、环境约束、运行参数和通过/停止条件。
- **Capacity Result**: 一次容量运行的事实、分位统计、资源峰值、瓶颈和适用范围。
- **Recovery Exercise**: 故障注入、预期影响、检测、接管、恢复步骤和验收结果。
- **Risk Entry**: 生产风险的触发条件、影响、检测、缓解、恢复验证、责任边界和剩余风险。

## 4. Cross-Cutting Semantics

### 4.1 Trace and Correlation Boundary

- 外部关联值只作为候选输入，必须校验后才能继承；平台内部标识由可信入口控制。
- tenant、user、session、message 和配置版本使用受控摘要或引用关联，不把原值复制到普通遥测。
- 节点接管时保留原请求关联，同时创建独立执行关联，以解释“同一业务请求、不同执行尝试”。
- 回复成功只在渠道确认既有发送成功语义后记录；结果未知必须保持未知，不能记成成功。

### 4.2 Audit and Telemetry Boundary

- Audit Log 是不可变、受权限控制的业务与安全事实；普通日志、指标、追踪和 Operational Event 是运行诊断。
- 普通遥测可以采样、聚合或在有界缓冲溢出时丢弃，但必须暴露丢弃计数。
- 需要正式审计才能授权的操作，在 Audit 不可用时继续沿用既有 fail-closed 规则；运行事件不能降低该门槛。
- 任何观察面都必须先脱敏再输出，禁止依赖下游平台进行首次脱敏。

### 4.3 Health and Error Semantics

- `alive` 只表示进程能够响应，不代表能够接收业务流量。
- `ready` 表示当前实例所承担角色具备安全处理新工作的全部关键依赖。
- `degraded` 表示普通遥测等非关键能力或单一渠道受损，但至少一条业务路径仍能安全完成；状态必须列明影响范围。
- `unready` 表示该实例继续接收新工作可能破坏正确性、安全或恢复语义，必须退出其流量接收集合。
- 平台整体状态按可用业务路径汇总：一个渠道或一个节点失效不得掩盖为全平台正常，也不得让其他健康渠道和节点无故退出服务。
- 对外错误使用稳定分类；内部异常、地址、堆栈和凭证只进入经过脱敏和授权的诊断边界。

### 4.4 Release and Rollback State

- 配置发布至少经历草稿、已验证、灰度中、暂停、已生效、回滚中、已回滚或失败等可解释状态。
- 状态转换必须幂等，且只能由当前权威版本和授权主体推进。
- 灰度与回滚以租户为最小业务作用域；不得因一个租户失败而静默改变其他租户配置。
- 安全与一致性硬门槛零容忍并自动止损；质量门槛必须带观察窗口和最小样本，越线只自动暂停并等待授权决定。
- 回滚在新请求边界生效；在途请求固定原配置版本以避免混用，但未执行副作用仍受当前治理和安全门禁约束。
- 软件回滚不得执行破坏性数据库降级；不兼容节点通过退出就绪避免读错新事实。

## 5. Acceptance Matrix

1. **双 IM 完整追踪**: 飞书和企业微信各完成单聊与群聊明确 @ 的成功/拒绝/重复消息，所有适用阶段可按关联标识还原。
2. **双租户隔离**: 两个租户使用相同业务键，日志、指标、追踪、健康、发布与审计查询均无串用。
3. **多节点接管**: 首节点在处理关键阶段退出，第二节点接管后不重复 Agent、Tool、数据写入或回复，轨迹解释 generation/fencing 结果。
4. **遥测出口故障**: 出口断连和缓冲溢出不会泄露数据或无限阻塞；降级与丢弃数量可见，正式审计边界保持不变。
5. **依赖故障矩阵**: 配置、Redis、PostgreSQL、Audit、IM 连接和 IM 发送故障均产生正确 readiness、稳定错误与恢复事件。
6. **灰度与回滚**: 目标租户使用新版本、范围外租户不变；失败门槛暂停推进；回滚后新请求统一使用旧版本且历史事实不变。
7. **容量证据**: 固定负载至少覆盖 2 个租户、2 个 Worker、100 个并发 Session 和 1,000 条消息；正确性结果全部为零，启用完整可观测性相对同机基线的吞吐下降和分位延迟增幅均不超过 10%；该规模是验收负载而非生产承诺。
8. **安全停机**: Worker 撤销就绪后无新任务进入，在途任务完成、移交或进入既有恢复状态，最终无无法解释的重复副作用。
9. **风险演练**: 至少八项风险全部有检测、缓解和恢复验证，其中至少四项有自动化或可重复人工演练证据。
10. **最终回归**: 前七阶段及第八阶段测试无未解释失败；任何跳过项都明确外部条件、影响和补测步骤。

## 6. Success Criteria

### Measurable Outcomes

- **SC-001**: 验收中的成功、拒绝、重复、冲突、接管和失败请求，100% 能通过一个安全关联引用还原其适用处理阶段与最终结果。
- **SC-002**: 双租户测试中跨租户日志、指标、追踪、发布状态和审计返回数量均为 0。
- **SC-003**: 预置 Secret、Token、response URL、手机号、邮箱和消息原文在所有可观察输出及 Git 候选文件中的未脱敏命中为 0。
- **SC-004**: 所有 README 指定的指标类别都有明确名称、单位、结果枚举、标签白名单和至少一个成功及失败样本。
- **SC-005**: 关键依赖故障在 30 秒内反映为正确的就绪或降级状态；恢复稳定后 60 秒内关闭对应活动告警。
- **SC-006**: 一次租户级配置灰度可在不影响范围外租户的情况下完成；硬门槛首次命中即停止扩大范围，质量门槛越线时停止推进；触发回滚后 5 分钟内，所有目标租户的新请求统一使用已知良好版本。
- **SC-007**: 固定的 2 租户、2 Worker、100 并发 Session、1,000 消息验收负载完成后，业务结果丢失、跨租户串用和不可解释重复副作用均为 0；任一非零即阻断完成声明。
- **SC-008**: 在同一机器、配置和确定性负载下，启用完整可观测性造成的吞吐下降和端到端分位延迟增幅均不超过 10%；任一越线即阻断完成声明，且不得用本地结果声明生产绝对容量。
- **SC-009**: 最小部署能够从干净环境按文档启动、验证、排空并停止；步骤中无需把任何 Secret 写入仓库或命令输出记录。
- **SC-010**: 至少八项生产风险完成结构化登记，至少四项完成可重复故障演练，恢复后租户隔离和幂等不变量破坏数量为 0。
- **SC-011**: README 总体验收项到规格、设计、代码、测试和证据的追踪覆盖率为 100%，模拟、真实和仅设计状态均有明确标识。
