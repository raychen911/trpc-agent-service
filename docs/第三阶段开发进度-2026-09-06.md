- 企微 Python 客户端的重连参数 `0` 实际表示无限重试，不能用它关闭重连。本实现由平台监测断线并关闭整个公开客户端，再释放账号 lease；库内重连设置为一次且延迟启动。真实网络中断/被踢实验仍待完成。
- Telegram `message_id` 是消息回执；企微 `req_id + errcode=0` 只标为协议确认，不伪造外部消息 ID 或已读回执。
- 上游原生 Session 原子 fencing/CAS 缺口仍保留生产执行门禁。本轮没有增加绕过门禁的开关。

协议依据：[企微官方实现](https://github.com/WecomTeam/aibot-node-sdk)、[Telegram Bot API](https://core.telegram.org/bots/api)。LangBot/TGO、Chatwoot、Dify/FastGPT/MaxKB、ZITADEL、Kubernetes/Outbox/OTel 等参考仓库的分工仍以主开发文档 §3.1 为准。

## 3. 身份、准入和可靠性

`actor_id` 保留真实操作者的匿名身份，用于授权与审计。SDK `user_id` 改为包含 tenant、Binding、app、单聊/群、话题、个人/共享模式和 epoch 的存储 scope，防止个人 Memory 在其他群中被自动检索。共享群可以共享存储 scope，但发送者 actor 不合并。

事件记录、加密回复上下文、Inbox 和 Telegram offset 在同一数据库事务提交。拒绝和忽略事件也被记录，防止它们阻塞轮询或在重试时进入 Agent。未授权正文不进入 Inbox。

账号归属表保留 `(channel, external_account_id) → tenant/Binding` 的永久关系。owner lease 采用数据库时钟和递增 generation；旧 owner 不得继续录入事件。生产通道进程要求 PostgreSQL，SQLite 仅用于开发组件测试。

每次网络发送前记录 `sending`。显式拒绝可按分类重试，超时、丢 ACK 或进程中断留下的在途发送归为 `delivery_unknown`。未知结果和永久失败会阻塞同一会话后续回复，待后续人工处置能力完成。当前不会自动重跑 Agent 来补发。

当前仅发送最终文本。Telegram 按 4096 字符分片；企微超过单条流式文本上限时标记待处理错误，不静默截断。媒体和更完整渲染属于 W08。

旧模拟 Inbox/Outbox 消费器排除已绑定 IM receipt 的消息，因此不会把真实 IM 请求送入 SimulationModel，也不会用模拟渠道回执代替真实投递。

当前 Channel 进程通过共享的 IMIngress 模块直接完成数据库准入事务，尚未实现主方案中的内部 Gateway RPC 与工作负载认证；因此 W03 仍按部分完成记录。后续拆分必须保留现有原子准入与 owner fencing 验证。

## 4. 数据库初始化与升级

新空数据库：配置 `TRPC_DATABASE_URL` 后执行 `python -m trpc_service._cli migrate`。当前 schema 版本为 5。版本 3/4 的离线增量升级见持久审批实现文档，不能让新代码直接连接未升级的历史库。

已有第二阶段数据库：

1. 停止 Gateway、Worker、Dispatcher、Post-turn、迁移任务等写入者；排空输入、回复和派生任务，核对未知工具副作用。
2. 备份平台数据库以及原生 Session/Memory 和对象/向量资源，确认能够恢复。升级工具不能替操作者证明外部写入者已经停机。
3. 在备份副本先验证 `python -m trpc_service._cli upgrade-schema --offline --backup-id 已验证备份标识`。
4. 工具检查旧表结构、未结束工作和 Session lease，添加新表与版本记录，保留旧数据/不可变配置，暂停旧租户及 Binding。
5. 显式发布新的配置版本后重新启用。新范围默认不继承旧个人记忆；需要保留历史时，必须另行完成明确身份映射方案。
6. 出错时使用已验证备份恢复，不依赖新旧代码兼容双写。

本轮只升级了测试库，没有操作正在运行的第二阶段数据库。启动文档中的历史命令需先满足此版本门槛。
