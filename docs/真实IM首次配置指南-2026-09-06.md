# 真实 IM 首次配置指南

适用对象：第一次创建企业微信机器人、Telegram Bot 的本项目开发者。

## 飞书凭据补充（2026-09-07）

用户已创建并发布飞书应用。新增专用隐藏输入命令，App ID 通过参数提供，App Secret 只在本机终端输入：

```powershell
.venv\Scripts\python.exe -m trpc_service._cli configure-feishu --app-id cli_你的应用ID
```

凭据保存至被 Git 忽略的 `.secrets/feishu.json`，字段为 `TRPC_FEISHU_APP_ID`、`TRPC_FEISHU_APP_SECRET`。不会覆盖既有 `.secrets/im.json` 中的企微、模型、身份或加密配置；目标文件已存在时拒绝覆盖。终端无法隐藏输入时拒绝保存，避免退化为明文回显。

此命令只保存本地凭据，不验证 App ID / Secret、不创建连接，也不订阅或发送消息。飞书通道适配和真实联调仍待完成；发布应用不能替代服务端接线。保存后再完成长连接事件订阅和真实收发验证。

第三阶段仍在开发：已具备真实协议客户端、通道进程、预算与持久化基础，并新增[隔离的真实文本链路联调命令](第三阶段真实文本链路实现-2026-09-06.md)。完整审批、管理 UI 和生产联合验收尚未完成，保存凭据后需按联调步骤验证对话。

## 1. 创建 Telegram 测试机器人

1. 打开 Telegram，进入官方 [@BotFather](https://t.me/BotFather)。不要向名称相似的第三方机器人发送凭据。
2. 发送 `/newbot`。
3. 按提示填写显示名称，例如 `My Agent Test`。
4. 按提示填写唯一用户名，通常以 `bot` 结尾。
5. BotFather 返回一段 Token。保存到自己的密码管理器，不要粘贴到聊天、截图或仓库。
6. 点击 BotFather 提供的机器人链接，打开你刚创建的机器人，点击「开始」。

这些步骤依据 [Telegram 官方入门教程](https://core.telegram.org/bots/tutorial#obtain-your-bot-token)。Token 用于程序访问 Bot API，与个人账号的登录验证码不同。

首次联调选择单聊和长轮询。长轮询由本机程序主动连接 Telegram，不要求配置公网 webhook 地址。运行机器需要能够访问 Telegram Bot API。创建机器人后，在服务连接并完成成员授权之前，不会自动收到 Agent 回复。

## 2. 创建企业微信测试机器人

按导师提供的界面操作：

`工作台 → 智能机器人 → 创建机器人 → 手动创建 → API 模式 → 页面底部 API 配置 → 使用长连接`

保存 **Bot ID** 和 **Secret / BotSecret**。这里不使用传统自建应用的 CorpID/AgentID，也不使用群机器人的单向 webhook URL。

该路径来自导师的截图；协议实现参考 [企业微信官方 Node SDK](https://github.com/WecomTeam/aibot-node-sdk)。本项目 Python 客户端固定为 `wecom-aibot-sdk-python==0.1.7`，其第三方维护属性与官方 tRPC SDK 分开标注。

长连接由服务主动连接企微，初次联调不用准备公网回调域名。先使用专门测试机器人和测试会话。

## 3. 准备模型信息

从已经开通的模型平台取得以下三项；暂时没有可以先跳过：

| 项目 | 填什么 |
|---|---|
| 模型名称 | 平台提供的模型标识，不能任意填写显示名称 |
| API Base URL | 平台文档给出的 API 基础地址，不附带 API Key |
| API Key | 模型访问密钥，通过隐藏输入保存 |

本轮只保存模型信息，尚未把它接入完整的共享预算和生产执行流程。

## 4. 在本机保存配置

在本仓库目录打开 PowerShell，执行：

```powershell
.venv\Scripts\python.exe -m trpc_service._cli configure-im
```

向导会逐项提问，密钥输入不会显示。暂时没有的机器人或模型，可以按回车跳过。它会生成 `.secrets/im.json`，并自动生成会话身份密钥和回复上下文加密密钥。

- 本操作不访问 IM、不发送消息，也不创建租户。
- `.secrets/` 已被 Git 忽略；文件仍然含有本地明文凭据，请保管好，不能提交或分享。
- 重复运行不会覆盖已有文件，避免丢失身份和加密密钥。
- 后续补充配置时编辑本机文件中对应字段，保留 `TRPC_IDENTITY_KEY` 和 `TRPC_IM_CONTEXT_KEYS`。不要重新生成这两项来“修复连接”。
- 这是本地开发入口。生产环境需要按开发方案完成受管秘密存储和轮换流程。

后续进程可以通过 `--secrets-file .secrets/im.json` 加载这一文件。它只允许加载本项目的 IM/模型/身份变量，不允许注入 `PATH`、`PYTHONPATH` 等进程控制变量。

## 5. 凭据和租户绑定的关系

你不需要把真实 Token 写进开发文档。管理配置只保存以下引用：

| 内容 | 本地变量 | Binding 中的配置 |
|---|---|---|
| Telegram Token | `TRPC_TELEGRAM_BOT_TOKEN` | `bot_token → env://TRPC_TELEGRAM_BOT_TOKEN` |
| Telegram Bot ID | `TRPC_TELEGRAM_BOT_ID` | 填入 `external_account_id`；向导提取，启动时再用 getMe 校验 |
| 企微 Secret | `TRPC_WECOM_BOT_SECRET` | `bot_secret → env://TRPC_WECOM_BOT_SECRET` |
| 企微 Bot ID | `TRPC_WECOM_BOT_ID` | 填入 `external_account_id` |
| 模型 Key | `TRPC_MODEL_API_KEY` | `api_key_ref: env://TRPC_MODEL_API_KEY` |

同一个外部 Bot 只能绑定一个租户/Binding。两个通道需要两个 Binding，各自选择 `wecom_ws` 或 `telegram_polling`。`transport: none` 表示尚未启用真实接入。

虽然长连接和轮询不用公网回调地址，配置中的 `webhook_public_id` 仍保留为平台路由标识；它不是 Telegram Token，也不是企微 Secret。

## 6. 首次连接后的成员授权

机器人第一次收到某个用户的消息，默认拒绝进入 Agent 执行。服务只记录事件标识、匿名 actor_id 和 `membership_required` 原因，不保存未授权正文。

目前已有受 operator 认证保护的后台接口：

1. `GET /admin/tenants/{tenant_id}/im/events` 查找这次测试事件和 actor_id。
2. `PUT /admin/tenants/{tenant_id}/im/bindings/{binding_id}/members/{actor_id}` 授权，首次请求为 `{"active":true,"grants":["chat"],"expected_epoch":0}`。
3. 授权完成后，再向机器人发送一条新消息。旧的拒绝事件不会因为重试而变成新的执行。
4. 撤销时使用当前 `authz_epoch`，更新 `active:false` 和空 grants。

最终管理 UI 会提供对应的“发现用户 → 授权 → 撤销”操作。当前还没有该 UI，不要求你手工调用接口完成联调；先完成前四节的账号和本机凭据准备即可。

## 7. 当前部署边界

### 独立连通测试

保存本机凭据后，可先验证企微收发，无需平台数据库或模型：

```powershell
.venv\Scripts\python.exe -u -m trpc_service._cli wecom-test --secrets-file .secrets/im.json --test-timeout 300
```

认证成功后，终端显示一次随机测试口令。打开机器人的单聊发送完整口令；只对匹配口令回复一次固定测试文本，群消息和其他聊天不回复。获得企微协议 ACK 后退出；丢 ACK 不自动重发。这个短时测试入口不适合与同一 Bot 的正式通道进程同时运行。

2026-09-06 已实际验证一个用户提供的企微 Bot：长连接认证、接收匹配的单聊口令、固定 stream 最终回复及协议 ACK 均成功。ACK 不代表用户已读，不代表完整 Agent/工具/持久任务链路已经验收。

本次新增的 OpenRouter 模型测试入口仅执行一条固定提示：

```powershell
.venv\Scripts\python.exe -u -m trpc_service._cli model-test --secrets-file .secrets/im.json
```

使用官方固定版本 SDK 的 OpenAIModel，模型固定为 `deepseek/deepseek-v3.2`，输出上限 32 tokens；SDK/HTTP 重试与供应商回退关闭。请求设置 OpenRouter 单价筛选，分别不超过每百万输入 $1、输出 $2；这属于供应商选择条件，不等于平台预算已经完成真实账单核对。规则依据 [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)。

这个模型测试需要主动执行，可能产生少量费用。它独立于企微固定回复测试，尚不把两者连接成完整 Agent 对话。

2026-09-06 已完成一次真实 OpenRouter 请求，官方 SDK 收到 DeepSeek 文本回复，usage 为输入 11、输出 3 tokens。实际费用尚未对账。连通结果记录在 `reports/live-connectivity-2026-09-06.json`，不含凭据或用户消息正文；两种测试入口的 4 项本地协议检查见 `reports/live-probes-contract.xml`。

### 服务进程

独立通道入口为 `python -m trpc_service._cli channel --secrets-file .secrets/im.json`，还依赖已经初始化的 PostgreSQL、已发布租户和后台成员授权。

此入口目前负责收取真实事件和消费真实 IM 投递账本。现有模拟 Worker 不会消费这些真实 IM 输入，也不会替代真实模型回复。完整双 IM Agent 往返、危险工具审批和预算验收完成前，不把这个入口作为生产上线步骤。

如果已经有第二阶段数据库，不能直接把新镜像覆盖运行。新服务会拒绝无版本的旧 schema。先参考开发进度文档中的停写、备份与显式升级流程；当前正在运行的第二阶段演示环境没有被本轮升级。
