# 架构

## 1. 一级架构

一级架构只表示模块之间的关系，不展开模块内部实现。

```mermaid
flowchart LR
    USER[IM 对话者]
    PLATFORM_ADMIN[平台管理员]
    TENANT_ADMIN[租户管理员]
    ACCESS[接入层<br/>Channel Adapter / Gateway]
    CONTROL[控制面<br/>Admin API / 配置管理]
    RUNTIME[执行层<br/>Worker / Filter / Runner]
    STORAGE[存储层<br/>Storage Adapter]
    EXTERNAL[外部能力<br/>Model / Tool / MCP]
    GOVERNANCE[治理层<br/>Telemetry / Audit / Alert]

    USER --> ACCESS --> RUNTIME
    PLATFORM_ADMIN --> CONTROL
    TENANT_ADMIN --> CONTROL
    CONTROL -. 配置快照 .-> ACCESS
    CONTROL -. 配置快照 .-> RUNTIME
    RUNTIME --> STORAGE
    RUNTIME --> EXTERNAL
    RUNTIME --> ACCESS --> USER
    ACCESS -. Trace / Metric .-> GOVERNANCE
    RUNTIME -. Trace / Audit .-> GOVERNANCE
    STORAGE -. Storage Metric .-> GOVERNANCE
```

## 2. 二级架构

### 2.1 控制面

```mermaid
flowchart LR
    PA[平台管理员] --> AUTH[认证 / RBAC]
    TA[租户管理员] --> AUTH
    AUTH --> API[Admin API]
    API --> PLATFORM[平台边界<br/>Tenant / Model Catalog / Credential<br/>Tenant Model Profile / Adapter Type]
    API --> TENANT[租户授权边界<br/>Agent / Channel Binding / Knowledge<br/>MCP Connection / Skill Grant]
    PLATFORM --> DB[(PostgreSQL<br/>Control Schema)]
    TENANT --> DB
    API --> AUDIT[(Management Audit)]
    DB --> SNAPSHOT[配置快照]
    SECRET[SecretStore<br/>租户密钥 AES-256-GCM] -. SecretRef .-> SNAPSHOT
    SNAPSHOT -. config_version .-> GATEWAY[Gateway]
    SNAPSHOT -. config_version .-> WORKER[Worker]
```

平台管理员统一管理模型凭据和租户模型策略，租户管理员不能修改模型或 API Key。租户管理员维护本租户 IM Binding、知识库、MCP Connection 和 Agent 能力授权。平台进入其他租户业务范围时必须携带支持原因并写入审计。IM 与 MCP 密钥按租户、用途分别加密保存，业务表只保存不可反查明文的 `SecretRef`。

一个 Tenant 只关联一个租户管理员登录身份。IM 对话者只在 Channel Identity、Conversation 和 Session 中建模，不属于控制面的管理账号或角色。

### 2.2 核心执行链路

```mermaid
sequenceDiagram
    autonumber
    actor User as IM 对话者
    participant IM as 企业微信 / 飞书 SDK
    participant Channel as Channel Runtime
    participant Queue as PostgreSQL Task Queue
    participant Worker as Agent Worker
    participant Platform as Identity / Config / Filter
    participant Cache as Redis 近期会话缓存
    participant Runner as tRPC-Agent Runner
    participant Capability as Model / RAG / Tool / MCP
    participant Store as Session / Ledger / Outbox

    User->>IM: 发送文本、图片或文件
    IM->>Channel: 长连接事件
    Channel->>Platform: Binding 就绪校验、身份与 Conversation 映射
    Channel->>Queue: 幂等写入 Agent Task（固定 config_version）
    Queue-->>Channel: 已持久化
    Channel-->>IM: 快速 ACK / 正在思考
    Note over Channel,Store: tenant_id、agent_app_id、request_id、trace_id、session_id 全链路传递
    Worker->>Queue: 按 Session FIFO 领取任务与 lease generation
    Worker->>Platform: 加载不可变配置，检查预算、权限与输入策略
    Platform-->>Worker: TenantContext + PolicyDecision
    Worker->>Store: 创建 Runner Attempt / Checkpoint，取得 Session version
    Worker->>Cache: 按 Tenant + Agent + Session + version 读取
    alt 缓存命中且版本一致
        Cache-->>Worker: 近期 Session Snapshot
    else 缓存未命中、过期或不可用
        Worker->>Store: 读取权威 Session / Memory
        Worker->>Cache: 回填有 TTL 的近期快照
    end
    Worker->>Runner: 按 user/model 轮次恢复历史，注入 Workspace、Skill 与已授权工具
    alt 直接模型问答
        Runner->>Capability: 调用租户 Model Profile
        Capability-->>Runner: 模型结果
    else 知识检索
        Runner->>Platform: knowledge.list / knowledge.search 授权
        Platform->>Capability: 按 Tenant + Knowledge Base 检索
        Capability-->>Platform: 带来源的命中结果
        Platform-->>Runner: 有界检索结果
    else 本地 Tool 或远程 MCP
        Runner->>Platform: Capability Grant + 风险判定
        alt 未授权
            Platform-->>Runner: 安全拒绝，不调用实现
        else 变更型 L2/L3 需要确认
            Platform->>Store: 创建绑定原请求的 Approval
            Platform-->>Runner: 返回确认短码并结束本轮
        else 已授权只读或已经确认
            Platform->>Store: Tool Ledger PREPARED
            Platform->>Capability: 执行 Tool / MCP
            Capability-->>Platform: 结果 / 明确失败 / 结果未知
            Platform->>Store: Tool Ledger SUCCEEDED / FAILED / UNKNOWN
            Platform-->>Runner: 有界结果
        end
    end
    Runner-->>Worker: Agent Event + 最终文本 + Token Usage
    Worker->>Store: 原子提交 Event、State、Inbox、Runner Request、Reply Outbox
    Worker->>Cache: 提交成功后更新 Session Snapshot
    Note over Worker,Store: Usage Ledger 与运行审计使用独立短事务；当前不创建 Memory/Audit Outbox
    Channel->>Store: Delivery Worker 领取 Reply Outbox
    Channel->>IM: 文本、回复流或 CardKit
    IM-->>User: 最终回复
```

Worker 不保存本地会话。同一个 Session 使用确定性路由键、队首领取、执行租约和数据库版本检查，避免跨节点乱序或并发写入。模型历史按原始 `message.received=user`、`agent.replied=model` 轮次恢复，当前问题始终作为单独的新 `user` 消息提交，不能把整段历史伪装成当前输入。

### 2.2.1 两种 IM 的差异

| 维度 | 企业微信智能机器人 | 飞书机器人 | 平台统一部分 |
| --- | --- | --- | --- |
| 连接 | API 模式长连接，Bot ID + Bot Secret | WebSocket 长连接，App ID + App Secret | Binding、密钥加密和配置热加载 |
| 会话 | 私聊、群聊 `@机器人` | 私聊、群聊 `@机器人`、话题线程 | Principal、Conversation、Session 映射 |
| 快速响应 | 回复流中的 `thinking_message` | 独立可见 ACK | 只在任务持久化成功后发送 |
| 最终文本 | 企业微信回复流 | CardKit 流式卡片 | Reply Outbox、重试、UNKNOWN/DLQ |
| 媒体 | 图片/文件等分片收发 | 图片/文件下载与发送 | Artifact 大小限制、租户对象键和媒体校验 |
| 平台限制 | 分片、回复流状态、平台限频 | CardKit 权限、事件订阅、平台限频 | Adapter 分类错误，Delivery Worker 统一恢复 |

Provider SDK、帧格式和媒体接口留在各自 Adapter 中；Agent 就绪检查、身份映射、任务幂等、执行、治理和可靠回复不能在 Adapter 内重复实现。

### 2.3 存储层

```mermaid
flowchart TB
    SERVICE[Session / Memory / Knowledge / Artifact / Audit Port]
    ROUTER[Storage Router<br/>按租户和能力选择后端]
    SQL[(PostgreSQL 18 + pgvector<br/>事实数据 / 向量 / Outbox / Audit)]
    REDIS[(Redis 8.2<br/>近期 Session Snapshot / 可选协调)]
    VECTOR[(可选外部 Vector Store<br/>大规模 Knowledge / Memory 索引)]
    OBJECT[(S3 兼容对象存储<br/>Artifact / 原始文档)]
    MEMORY[外部 Memory 服务]

    SERVICE --> ROUTER
    ROUTER -->|强一致事务| SQL
    ROUTER -->|精确版本缓存，失败回源| REDIS
    ROUTER -. Outbox 投影 .-> VECTOR
    ROUTER -. Outbox 投影 .-> OBJECT
    ROUTER -. 可选同步 .-> MEMORY
```

PostgreSQL 是核心事实源，也是当前任务、Session 租约与 Outbox 的正确性依赖。Redis 已接入 Worker 的近期 Session Snapshot 读写：SQL 在领取任务时给出权威版本，只有版本完全相同的缓存才可使用；未命中、过期、损坏或连接失败都回源 PostgreSQL。缓存只在 SQL 提交成功后更新，停用或丢失 Redis 不影响事实恢复。向量库、对象存储和外部 Memory 不加入分布式事务，派生写入失败时根据状态或 Outbox 恢复。

### 2.4 RAG 链路

```mermaid
flowchart LR
    ADMIN[租户管理员] -->|登录| WEB[租户管理台]
    WEB -->|显式上传 / 替换 / 删除| API[Knowledge API]
    API --> AUTH[租户角色 + Agent + 知识库授权]
    AUTH --> UPLOAD[Artifact Upload]
    UPLOAD --> OBJECT[(SeaweedFS<br/>原始文件)]
    UPLOAD --> META[(PostgreSQL<br/>Artifact 元数据)]
    UPLOAD --> PARSE[TXT / Markdown / PDF / DOCX]
    PARSE --> CHUNK[确定性切片与版本]
    CHUNK --> EMBED[百炼 text-embedding-v4]
    EMBED --> VECTOR[(pgvector<br/>tenant_id + knowledge_base_id)]
    META --> API
    USER[IM 对话者] --> IM[Channel Adapter]
    IM --> RUNNER[tRPC-Agent Runner]
    VECTOR --> RETRIEVE[knowledge.search Tool]
    RETRIEVE --> RUNNER
    RUNNER --> RESULT[正文 + 来源编号]
    API --> AUDIT[(Management Audit)]
```

知识库属于 Tenant，不属于单个 Agent。对象键、元数据和向量行都包含 `tenant_id`；Agent 只能读取配置快照中授权的 `knowledge_base_names`。上传、替换和删除只开放给租户管理员的显式 HTTP 接口，页面再次确认后提交，后端重新校验权限并记录审计。IM 模型侧只注册 `knowledge.list` 和 `knowledge.search`，即使旧配置残留写权限也不会创建写工具。更新生成新版本并失效旧向量，删除保留 Tombstone。

### 2.5 Skill、MCP 与 Tool

```mermaid
flowchart LR
    ADMIN[租户管理员] --> AGENT[Agent 能力授权]
    ADMIN --> MCP[MCP Connection<br/>URL / 加密凭据 / 工具目录]
    CATALOG[平台 Skill 目录] --> AGENT
    MCP --> AGENT
    AGENT --> RUNNER[tRPC-Agent Runner]
    RUNNER --> SKILL[SkillLoadTool<br/>仅加载操作步骤]
    RUNNER --> TOOL[本地通用 Tool]
    RUNNER --> REMOTE[MCPToolset<br/>远程租户工具]
    TOOL --> GOVERN[Capability Grant / Approval<br/>Tool Ledger / Audit]
    REMOTE --> GOVERN
```

Skill 是平台审核过的操作知识，当前只有 `hr-assistant` 和 `code-review`，通过 tRPC-Agent-Python 的 `FsSkillRepository` 与 `SkillLoadTool` 加载，不提供 Skill 执行或沙箱。MCP 由租户填写 HTTPS Streamable HTTP 地址和可选 Bearer Token，刷新后保存工具名称、Schema 和交互风险分类；凭据不回显。Agent 只能看到显式授权的 Skill 和 MCP Tool，MCP 实际调用仍进入统一治理链路。请求级装配以最新目录分类覆盖旧快照风险：严格声明为只读的 Tool 直接执行，未声明或变更型 Tool 按 L2 确认；SDK 返回的可恢复 Tool 错误继续交给模型修正，供应商或模型错误仍直接失败。

能力在每次请求中按不可变 Agent 快照重新装配，不使用跨租户的全局 Tool 实例：

```mermaid
sequenceDiagram
    autonumber
    participant Config as Agent Config Snapshot
    participant Factory as Request-scoped Factory
    participant Skill as FsSkillRepository
    participant MCP as Tenant MCP Catalog
    participant Agent as tRPC LlmAgent
    participant Guard as GovernedToolInvoker
    participant Ledger as Approval / Tool Ledger / Audit

    Factory->>Config: 读取 typed Capability Grants
    Factory->>Skill: 过滤允许 load 的 Skill
    Factory->>MCP: 按 Tenant、Connection、Tool 过滤目录
    Factory->>Agent: 注入 FunctionTool、SkillLoadTool、GovernedMCPTool
    Agent->>Guard: 调用本地 Tool 或 MCP Tool
    Guard->>Guard: 校验 kind、name、action、resource、risk
    alt 未授权
        Guard-->>Agent: 拒绝，不调用实现
    else 需要确认
        Guard->>Ledger: 创建绑定原请求的 Approval
        Guard-->>Agent: 返回一次性确认短码
    else 允许执行
        Guard->>Ledger: PREPARED
        Guard->>MCP: 调用本地实现或 tRPC MCPToolset
        MCP-->>Guard: 结果 / 明确失败 / 结果未知
        Guard->>Ledger: SUCCEEDED / FAILED / UNKNOWN
        Guard-->>Agent: 有界结果
    end
```

Skill 只提供经过审核的文字步骤，不经过 Tool Ledger，因为它没有外部副作用；本地 Tool 与 MCP 执行都经过同一个 `GovernedToolInvoker`。租户先显式授权具体连接和 Tool，随后 `readOnlyHint=true` 且未声明破坏性的读取按 L0 直通，其余 MCP Tool 保守归类为 L2。旧目录在首次使用时按策略版本自动重发现，失败时维持 L2。两类调用都保留 Tool Ledger、审计、指标、超时和租户隔离。

### 2.6 本地部署

```mermaid
flowchart LR
    subgraph Host[主机 Python + uv]
        API[Gateway / Admin API<br/>独立进程]
        SUPERVISOR[Worker Pool Supervisor<br/>期望状态协调]
        CHANNEL[Channel Runtime<br/>企业微信 / 飞书长连接]
        QUEUE[Agent Task Queue Port]
        WORKER1[Agent Worker 1<br/>独立进程]
        WORKER2[Agent Worker 2<br/>独立进程]
        WORKERN[Agent Worker N<br/>水平扩展]
        WORKSPACE[(Local Workspace<br/>Tenant / Agent / Request)]
    end

    subgraph Compose[Docker Compose：仅基础设施]
        PG[(PostgreSQL + pgvector<br/>Session / Memory / Knowledge / Audit)]
        REDIS[(Redis)]
        OTEL[OpenTelemetry Collector]
        PROM[Prometheus 3.13 LTS]
        GRAFANA[Grafana 13.2]
        TEMPO[Tempo 3.0<br/>Trace 检索]
        LOKI[Loki 3.6<br/>日志存储]
        ALLOY[Grafana Alloy<br/>日志采集]
        OBJECT[(SeaweedFS<br/>S3 Artifact)]
    end

    CHANNEL -->|双 IM 持久化入队| QUEUE --> PG
    API -->|desired_nodes| PG --> SUPERVISOR
    SUPERVISOR -->|创建 / 排空| WORKER1
    SUPERVISOR -->|创建 / 排空| WORKER2
    SUPERVISOR -->|创建 / 排空| WORKERN
    PG -->|FOR UPDATE SKIP LOCKED| WORKER1
    PG -->|租约接管| WORKER2
    PG --> WORKERN
    API -. 可选协调 .-> REDIS
    WORKER1 --> PG
    WORKER1 -->|近期 Session 缓存| REDIS
    WORKER1 --> WORKSPACE
    WORKER2 --> WORKSPACE
    WORKERN --> WORKSPACE
    PG -->|IM Reply Outbox| CHANNEL
    API -. Telemetry .-> OTEL
    WORKER1 -. Telemetry .-> OTEL
    WORKER2 -. Telemetry .-> OTEL
    CHANNEL -. Telemetry .-> OTEL
    OTEL -->|聚合指标| PROM --> GRAFANA
    OTEL -->|Trace| TEMPO --> GRAFANA
    API -. JSON Log .-> ALLOY
    WORKER1 -. JSON Log .-> ALLOY
    CHANNEL -. JSON Log .-> ALLOY
    ALLOY --> LOKI --> GRAFANA
    WORKER1 -. Artifact .-> OBJECT
```

`start.sh` 当前启动一个 Gateway、一个统一 Channel Runtime 和一个 Worker Pool Supervisor；Supervisor 首次以两个 Worker 为期望值，随后以管理端保存的 `desired_nodes` 为准创建独立 Worker。缩容节点先进入 `draining`，停止领取新任务并在完成当前任务后退出。Channel Runtime 同时管理企业微信与飞书长连接；入口先映射租户 Principal、Conversation 和 Session，再写入 `agent_task`。Worker 通过 SQL 行锁、FIFO 路由、lease generation、Runner Attempt 和 Checkpoint 执行；Session Fence 与 State version 阻止旧节点提交。节点不保存 Session，也不要求 sticky session。

Local Workspace 位于 `data/workspaces/<tenant>/<agent>/<request>`。每次 Worker 开始执行时都会获取同一个 Request Workspace，并将类型化 `WorkspaceHandle` 注入 Runner Context；因此本地 Worker 1 失败后，Worker 2 可按稳定 Request ID 接管同一目录。目录内固定包含 `inputs`、`outputs`、`tmp`，只通过 `WorkspaceProvider` 暴露；路径穿越、绝对路径和越界符号链接默认拒绝，当前仅开放受治理的列表与只读文本 Tool。

本地模式不运行应用 Python 容器，只有基础设施进入 Compose；Kubernetes 模式使用项目 `Dockerfile` 构建 Python 3.12 应用镜像。PostgreSQL 是任务、完整会话、Worker Pool 期望状态和 Usage Ledger 的事实源；Redis 保存带 TTL 的近期 Session 快照并允许随时从 SQL 重建，不能替代 `agent_task` 或完整事件日志。Prometheus 保存低基数指标，Tempo 保存 Trace，Loki 保存结构化日志，Grafana 统一查询但不充当数据源。Kubernetes 使用单独的最小权限 Scaler 修改 `agent-worker` Deployment 的 scale 子资源，控制面语义与本地 Supervisor 一致。
