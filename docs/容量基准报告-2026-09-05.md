# 容量基准报告：2026-09-05

## 条件与统计口径

实际执行环境：Docker Desktop / WSL2 Linux，Python 3.12.14，进程可见 22 个逻辑 CPU；容器 cgroup 未单独限制 CPU/内存。每个并发档位独立初始化平台 schema，单 Python 进程执行，包含首次调用冷启动影响；共享后端为 PostgreSQL 和 Redis。每档 48 条不同 Session 消息、两个租户，附加 10 次相同消息重投。每条经过可信路由、真实 Inbox、Runner、LlmAgent、FunctionTool、Session 写入、平台提交与 Outbox。

模型每次调用等待 50ms，每消息调用两次并执行一个只读工具。usage 为显式模拟值：每次 input=200、output=50，每条合计 500 token；没有调用付费模型。结束点是 Outbox 就绪，尚未实际发送 IM、消费 Post-turn 或写完整业务 Audit。每档均产生 144 条待投递 Outbox。

这是一次有限突发负载样本，不是稳态持续压测，也没有固定每节点资源配额；48 个样本的 P99 不能作为可靠生产尾延迟估计。不能直接把并发档位认定为生产安全 session 数。

归一化后的入站落库路径测到约 326–449 ops/s，入口在 Worker 消费前集中写入有限突发；它不包括实际网络/SDK 验签、HTTP 服务并发和企业微信限频，不能宣称为 IM 回调峰值上限。

## 解释与下一轮实验

本样本并发 4 的吞吐最高，继续提高并发主要增加执行等待。Redis 档的事件循环延迟 P95 从并发 4 的 98.5ms 增至并发 16 的 487.0ms；SQL 档从 251.3ms 增至 738.5ms。代码中的同步 SQL repository 在 async 执行路径直接运行，这是阻塞来源的一个解释，尚需 profiling 验证，不能仅凭相关性断言全部瓶颈在 SQL。

后续可以从每进程并发 4 作为调参实验起点；不得把它当最终生产配置。需对比异步数据库访问或受控线程执行、真正双 Worker、固定资源预算，再测 10–30 分钟稳态和故障重投。数据库每消息操作预算应增加 Dispatcher、Post-turn、Audit、续租和迁移负载。本轮未测这些消费者，不能据吞吐直接估算整个产品容量。

例如规划有效消息 10/s、每消息总计 1500 个真实 token、平均 3 次模型调用，则模型预算为 900,000 TPM、1,800 RPM。若平均耗时 2s、P95 4s、安全并发 20、目标利用率 50%，平均在途为 20、尾部预算为 40，公式给出 4 个 Worker；这是输入假设的算例，不是本轮实测结论。真实值需由目标模型 usage、延迟、配额和业务 SLO 替换。

SQL 每消息约 37 条（Redis Session 档）或 59 条（SQL Session 档），Redis Session 每消息约 12 条命令，均为本样本路径的粗预算；SQL 全局负载还含其他服务。Redis 计数使用官方 [INFO](https://redis.io/docs/latest/commands/info/) 的统计字段；同服务器其他业务会污染增量，因此共享生产环境不可直接用该值归因。

## 原始证据与复现

- [Redis Session 完整测量](../reports/capacity-redis.json)：包括均值、P50/P95/P99、SQL 延迟、事件循环延迟、CPU、token 和排队数据。
- [SQL Session 完整测量](../reports/capacity-sql.json)。
- [故障验收 JUnit](../reports/operations.xml)。
- 故障验收为 5 passed、1 failed；失败项是模型错误被标记为成功，不属于容量测量通过的范围。
- `tests/benchmarks/capacity.py` 为可执行基准；`tests/test_capacity_planning.py` 校验公式单位与 token 不重复累乘。

已构建 e2e 镜像的环境可以执行：

```sh
docker compose --profile test run --build --rm e2e \
  -m tests.benchmarks.capacity --backend redis --messages 48
docker compose --profile test run --build --rm e2e \
  -m tests.benchmarks.capacity --backend sql --messages 48
```

完整运维验收入口 `sh ops.sh` 会构建测试镜像、运行故障测试和两组基准，保存 reports，最后清理该独立项目的容器/网络并保留数据卷。存在已知故障断言时仍继续容量测量，最终返回非零状态；本轮实际复用了旧 integration 镜像并挂载新代码，未执行全新镜像构建。报告结果不是远端 CI 运行结果。
