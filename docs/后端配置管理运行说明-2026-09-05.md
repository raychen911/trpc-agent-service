# 后端配置管理运行说明

本轮补齐第二阶段的控制面纵向流程：运维登记存储配置 → 保存租户配置版本 → 校验并发布 → Gateway 使用当前版本路由 → Worker 按消息固定版本加载 → 查询操作审计。

使用官方 `trpc-group/trpc-agent-python` 固定版本，不引用、修改本地二开 SDK。本功能没有解除生产执行入口的原子 fencing 限制。

## 已实现的管理能力

| 接口 | 功能 |
| --- | --- |
| `POST /admin/backend-profiles` | 登记不可变的后端配置修订版，连接凭据使用 `env://` 引用 |
| `GET /admin/backend-profiles` | 分页查询配置元数据，排除连接密钥引用 |
| `GET /admin/tenants` | 分页查询租户状态及当前配置版本 |
| `POST /admin/tenants/{tenant_id}/configs` | 保存完整配置快照及六类资源的固定后端修订版 |
| `GET /admin/tenants/{tenant_id}/configs` | 查询版本列表 |
| `GET /admin/tenants/{tenant_id}/configs/{version}` | 查询快照及后端绑定修订版 |
| `POST /admin/tenants/{tenant_id}/configs/{version}/publish` | 使用 `expected_active_version` 原子发布，也可重新发布旧版本进行配置回滚 |
| `GET /admin/tenants/{tenant_id}/audit` | 分页查询管理审计，平台配置登记使用 `tenant_id=platform` |

分页参数为 `limit`（默认 100，上限 500）和 `offset`。配置快照包含 Agent 应用、模型参数、工具策略、渠道绑定及租户状态。修改时保存新版本，不原地编辑已有版本。

管理接口属于平台运维接口，使用独立的 `TRPC_ADMIN_TOKEN` Bearer 凭据；不是租户自助接口或多角色权限系统。未设置该变量时不挂载 `/admin`。`TRPC_ADMIN_ACTOR` 指定审计中的运维身份，默认 `platform_operator`。连接明文不写入配置；完整租户配置查询会返回原有的 SecretRef 引用。

## 启用数据库管理模式

基础 Compose 继续使用文件配置。管理模式必须在 Gateway、两个 Worker、Dispatcher、Post-turn 上统一启用 `TRPC_CONFIG_SOURCE=database`；不从文件自动导入或回退。

在 PowerShell 中设置至少 32 字符的随机运维凭据，然后启动：

```powershell
$env:TRPC_ADMIN_TOKEN = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
$env:TRPC_ADMIN_ACTOR = 'local_operator'
docker compose -f docker-compose.yml -f docker-compose.management.yml up -d --build gateway worker-1 worker-2 dispatcher post-turn
```

后续重建也需要提供相同的运维凭据，或通过受管理的环境配置注入新凭据完成轮换。不要把凭据写入仓库。

首次启用时，数据库中没有发布配置也能启动服务；此时渠道消息无法匹配租户。首次导入示例配置：

```powershell
.\.venv\Scripts\python.exe deploy/bootstrap_management.py
```

该脚本通过 HTTP 管理接口，读取 `deploy/management-profiles.json` 和 `deploy/simulation-tenants.json`，登记配置、保存草稿并以 `expected_active_version=0` 首次发布。它用于空控制面的首次初始化，遇到已有版本会停止并报告冲突，不覆盖现有数据。若中途失败，使用下述接口查询已保存的资源后继续剩余步骤。

随后打开 `http://localhost:8080/docs`，在 Authorize 中填入运维 token，使用 `operator management` 接口。保存草稿的请求结构为：

```json
{
  "config": "替换为完整 TenantConfig 对象",
  "profile_revisions": {
    "session": 1, "memory": 1, "summary": 1,
    "knowledge": 1, "artifact": 1, "audit": 1
  }
}
```

其中 `config` 必须是对象；具体结构以 OpenAPI 的 `ConfigDraft` 为准。发布新版本时提交 `{"expected_active_version":3}`，表示只有当前版本仍为 3 时才允许切换。初次发布使用 0。

## 发布与恢复语义

- 数据库保存配置快照、固定后端修订版、应用配置及审计。版本冲突返回 409，缺少配置返回 404，能力或配置校验失败返回 422。
- 后端必须支持绑定的资源能力和类型；禁止 InMemory；Session 与 Summary 必须使用同一后端配置及修订版。接口只接受当前部署已实现的 `env://VARIABLE` 引用，不接受 options、region 或 health 覆盖。
- 后端登记只校验声明及结构，不代表远端连通性探测。`endpoint` 用于登记展示；Worker 实际连接地址取自 SecretRef 所引用的环境变量。现有引用的连接目标应保持稳定，变更存储位置走迁移流程。
- 发布通过数据库条件更新竞争当前版本。渠道回调身份有数据库唯一约束；发布失败时当前版本、渠道绑定、审计一并回滚。
- Gateway 每次接收消息读取当前发布配置。消息接受后携带固定配置版本；Worker 按需构建该版本的 Runner，并保留已加载的版本。进程重启后，历史消息仍能从持久化配置恢复。版本缓存随进程关闭释放，目前没有在线淘汰策略。
- 将租户或应用设为停用后，新消息不再进入对应路由；已接受的消息继续按照接受时的配置完成。这不是紧急取消正在执行任务的接口。
- 再次发布旧配置可以回滚应用参数，但资源位置、后端修订版及 storage_revision 必须保持一致。管理接口不会执行存储搬迁。
- 模拟运行模式会拒绝发布外部模型、工具或知识检索配置，保持与已实现的 Worker 能力一致。六类后端都可登记和绑定；当前可部署 Worker 实际按绑定加载 Session、Memory、Summary，Knowledge/Artifact 与审计存储动态切换尚未接入该运行入口。

## 验证与范围

本轮真实存储全量回归：139 项通过，0 跳过；报告 `reports/management-real.xml`。其中 PostgreSQL 验证了两个并发发布只能有一个提交，失败发布不产生成功审计。管理测试还验证了新旧 Worker 的版本加载、原生会话延续、Post-turn、配置回滚、回调冲突、凭据隔离和快照持久化。

另补 Gateway HTTP 请求在发布前后分别固定版本、未配置运维凭据时管理接口关闭的测试。完整管理页面、租户级 RBAC、灰度发布、连接健康探测、任务人工处置及完整生产模型入口仍是后续工作，不能据此认定第二阶段全部完成。

本轮提交的是代码、部署配置与初始化入口；正在运行的基础容器不会自动升级，启用管理模式需执行上述重建命令。
