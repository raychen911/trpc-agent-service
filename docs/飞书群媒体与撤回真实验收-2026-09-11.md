# 飞书群媒体与撤回真实验收

日期：2026-09-11。范围限定为飞书群聊中的独立图片、独立文件和用户消息撤回。测试使用常驻 PostgreSQL、Redis、MinIO、一个 Channel 进程和两个 Agent Worker；不以模拟事件代替平台投递。

## 1. 平台前置配置

飞书企业自建应用使用长连接订阅，已发布以下事件：

- `im.message.receive_v1`（接收消息）
- `im.message.recalled_v1`（消息撤回）

应用身份权限查询返回单聊接收、群 @ 接收、机器人发送以及完整消息权限，状态均为已开通。群内独立图片和文件只有在“获取群组中所有消息”权限发布并重新建立长连接后才稳定投递。权限、事件订阅和应用版本发布是三个不同步骤，不能只配置其中一项。

## 2. 真实测试结果

| 场景 | 平台事件与处理结果 | 持久化证据 | 结论 |
|---|---|---|---|
| 独立图片 | `message_type=image`；Channel 回调成功；一个 Worker 完成执行并发送最终文本回复 | Inbox `succeeded`；17,171 字节 JPEG 写入 MinIO；Artifact 元数据为 `published` | 通过 |
| 独立文件 | `message_type=file`；Channel 回调成功；一个 Worker 完成执行并发送最终文本回复 | Inbox `succeeded`；236,875 字节 PDF 写入 MinIO；Artifact 元数据为 `published` | 通过 |
| 已完成消息撤回 | `im.message.recalled_v1` 到达；按原始 message ID 命中入站记录；回执 disposition 为 `recalled` | 原 Inbox 保持 `succeeded`，同时写入 `error_type=message_recalled` | 通过 |

图片和文件在入 Inbox 前完成下载、大小检查、摘要计算和对象存储发布；持久层只保存内部 Artifact URI，不保存飞书资源 key。两 Worker 共享 Inbox，测试记录的 `attempt=1`，未发生重复模型执行。

撤回发生时原消息已经执行完成并发送回复，因此系统不伪造业务回滚，也不把 `succeeded` 改写为失败。`message_recalled` 用于后续审计和阻止仍处于 pending/retry 的出站消息。协议与 PostgreSQL 测试已覆盖执行前撤回将 pending/retry/processing 输入置为 `failed_final`，但本次真实飞书测试不宣称命中了该短暂竞态窗口。

## 3. 连接恢复观察

文件回调提交后观察到一次飞书 WebSocket `ConnectionError`。Channel 进程未退出，账号租约 generation 从 42 增加到 43 并重新建立连接，随后继续接收文本和撤回事件。该结果证明本次断线后的自动重连有效，但不替代长时间断网、ACK 丢失或多 Channel 实例抢占测试。

## 4. 明确边界

- 飞书 `post` 富文本/混合内容仍按 `unsupported_media_post` 忽略；本次通过项是平台原生 `image` 和 `file` 消息。
- 图片内容理解、Agent 角色、提示词和回复语义由租户 Agent 配置负责；本次只验收媒体进入 Agent 的可靠链路。
- 机器人主动发送图片或文件、删除已经发送的机器人回复和消息卡片不在本次范围。
- 真实平台 429、长文本真实分段、执行中的真实撤回竞态仍未实测，不得写成已通过。
