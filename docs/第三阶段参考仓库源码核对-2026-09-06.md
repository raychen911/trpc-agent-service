# 第三阶段参考仓库源码核对

核对日期：2026-09-06。本文记录实际读取过的实现，区分本轮已落地和后续待采用内容。参考架构与行为后按本项目的数据模型实现；本轮未整段复制这些仓库源码，也未引入它们作为运行依赖。后续如需复用源码，须先核对对应版本许可证和署名要求。

## 1. LangBot：话题与连接生命周期

固定提交：`ec63978ecf46156d35e421145972d77c486aaed2`。

- [Telegram adapter](https://github.com/langbot-app/LangBot/blob/ec63978ecf46156d35e421145972d77c486aaed2/src/langbot/pkg/platform/sources/telegram.py)：核对 `send_message`、`reply_message`、`get_launcher_id`、`run_async`、`kill`。消息目标包含 chat 和 thread，回复保留 `message_thread_id`；启动、监听和关闭由适配器负责。
- [WeCom adapter](https://github.com/langbot-app/LangBot/blob/ec63978ecf46156d35e421145972d77c486aaed2/src/langbot/pkg/platform/sources/wecombot.py)：核对 `run_async`、`kill`，长连接启动和 disconnect 配对，Webhook 模式采用不同关闭方式。

本项目对应代码：`channels/telegram.py`、`channels/wecom.py`、`channels/runtime.py`、`tenant/routing.py`（均位于 `trpc_service/`）。普通消息和按钮事件均保留 Telegram 话题上下文；SDK Session/Memory scope 进一步包含租户、Binding、app 和会话模式。测试覆盖话题回复参数、按钮不会进入 Agent 正文及跨群隔离。

连接所有权还需满足本项目的多进程要求：数据库 lease/generation 控制唯一 owner，断线后关闭客户端再释放所有权。不能仅依赖单进程生命周期保证不会双收双发。流式编辑、媒体和卡片仍属于后续 W08/W06。

## 2. TGO：接收、标准化与投递分工

固定提交：`995da4577f6f91edb87d0f56fc9ea4c129f1a4eb`。代码在 `tgoai/tgo` 单体仓库的 `repos/tgo-platform` 下。

- [Telegram listener](https://github.com/tgoai/tgo/blob/995da4577f6f91edb87d0f56fc9ea4c129f1a4eb/repos/tgo-platform/app/domain/services/listeners/telegram_listener.py)：核对 `_load_active_telegram_platforms`、`_store_to_inbox`、`_build_mapped_message`、`_process_update`、`_poll_platform`、`_consumer_loop`。按已启用账号加载连接、将外部字段转成标准消息，再交给后续处理，是可参考的职责划分。
- [Telegram outbound adapter](https://github.com/tgoai/tgo/blob/995da4577f6f91edb87d0f56fc9ea4c129f1a4eb/repos/tgo-platform/app/domain/services/adapters/telegram.py)：核对 `send_incremental` 与 `send_final`；能力差异由通道处理，最终文本有独立发送入口。

本项目采用独立接收进程、标准事件和通道投递器，分别落在 `channels/runtime.py`、`channels/events.py`、`channels/delivery.py`。此版本参考代码的以下行为不适用于本项目验收：

| 参考版本行为 | 本项目处理 |
|---|---|
| 轮询位置保存在 `_platform_offsets` 内存字典 | 事件、Inbox 和 offset 同一数据库事务提交；拒绝和忽略也可推进 offset |
| 启动时自动删除现有 webhook | 检测到 webhook 后拒绝启动轮询，等待明确的切换操作 |
| 最终文本使用 `text[:4096]` | Telegram 分片发送，逐片记录回执和重试，不丢弃剩余文本 |
| 映射上下文携带 bot token，并打印部分消息内容 | 标准消息不携带 token；使用进程内凭据引用、加密回复上下文与受限日志 |
| 在处理过程中直接请求下游并发送 | 先持久接收，再独立执行和投递；发送未知结果进入待处理状态 |

这些差异由本项目“持续消费、故障恢复、密钥不进入日志”的要求决定，不代表对参考仓库整体能力的评价。

## 3. Chatwoot：账号、联系人、会话与外部回执

固定提交：`8314676d1bece93d24293e87e80c94e7f5494d67`。

- [IncomingMessageService](https://github.com/chatwoot/chatwoot/blob/8314676d1bece93d24293e87e80c94e7f5494d67/app/services/telegram/incoming_message_service.rb)：核对 `perform`、`set_contact`、`conversation_params`、`set_conversation`。联系人关联 inbox，会话保留 account/inbox/contact；消息保留 Telegram 原生 source ID。
- [SendOnTelegramService](https://github.com/chatwoot/chatwoot/blob/8314676d1bece93d24293e87e80c94e7f5494d67/app/services/telegram/send_on_telegram_service.rb)：核对 `perform_reply`、`inbox`、`channel`；从消息归属的 inbox 选择通道，实际取得 message ID 后更新回执。

本项目对应 `IMAccountRow`、`IMMembershipRow`、`IMEventReceiptRow`、`IMDeliveryAttemptRow`。账号归属与操作者身份分开，投递依赖原输入绑定的账号，Telegram 消息 ID 与企微协议 ACK 分开建模。

注意：此版本 Telegram 入口只处理 private message，不能直接满足本项目群聊要求。我们的 actor、群、话题与 SDK 存储 scope 分离；不能只凭外部 user ID 找到所有租户的历史会话。未来 UI 可参考“通道账号 → 用户 → 会话 → 消息状态”的组织关系，当前页面尚未实现。
