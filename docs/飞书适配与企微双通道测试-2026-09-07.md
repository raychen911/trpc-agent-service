# 飞书适配与企微双通道测试

日期：2026-09-07。按原 README 的“至少两类 IM，至少包含微信或企业微信”要求，实际账号验收组合调整为 **企业微信智能机器人 + 飞书企业自建应用机器人**。Telegram 代码及协议回归保留，不要求用户申请 Telegram 账号。此调整不引入额外业务系统。

## 1. 本批实现

新增 `channels/feishu.py`，接入既有 `ChannelRuntime`、`IMIngress`、账号租约、投递账本与审批通知。长连接只使用飞书官方 Python SDK `lark-oapi==1.7.3` 的公开接口。HTTP 使用固定飞书域名、超时和禁止重定向的客户端，不允许消息指定请求地址。

飞书 SDK 的公开 `Client.start()` 会阻塞，且没有公开停止接口，因此每个账号连接在服务拥有的子进程内运行。父进程负责 SQL 账号租约、续期、当前配置校验、消息入库和回复；取消、断线或持久化失败后，关闭连接子进程，再释放租约。通道运行器按既有 3–6 秒退避重新获取账号所有权并连接，不修改 SDK 的私有状态或事件循环。

子进程的消息回调通过 IPC 请求父进程入库，只有收到对应随机 nonce 的成功提交确认才返回，由 SDK 发送成功 ACK。父进程处理上限 1.5 秒，子进程等待上限 2 秒；超时、持久化异常或确认不匹配会使该连接退出。若 SQL 线程稍后完成，重投仍由唯一消息键去重。该机制依赖平台自身的重投窗口，不承诺无限重投或平台侧绝不丢消息。

## 2. 输入、身份与权限

订阅 `im.message.receive_v1` 与 `im.message.recalled_v1`，限定企业自建应用长连接。App ID 与连接的租户绑定必须一致；用户事件的 sender.tenant_key 必须与 header.tenant_key 一致。通过内部应用 token 获取机器人自身 open_id，用于精确判断群聊 @。本实现不提供飞书 HTTP webhook，不能把未经验签的 HTTP 数据送入该入口，也不把长连接认证描述为 HTTP 回调验签。

- 私聊：用户发送的非空文本归一化为 `NormalizedInboundMessage`。
- 群聊：只有明确 @ 当前机器人且剩余文本非空才入 Agent；@ 他人、普通群消息、机器人发送者不触发模型。
- 话题：保留实际 `thread_id`，回复使用官方消息 reply 接口的 `reply_in_thread=true`。
- 图片、文件：仅在成员授权通过后从固定飞书资源接口下载，限制为 20 MiB，写入租户对象存储后以内部 Artifact URI 进入 Agent；群文本仍要求 @，纯媒体因没有文本 @ 位置而按成员授权处理。
- 撤回：飞书撤回事件按企业、绑定、群聊和原消息 ID 定位；取消未完成输入并阻止未发送回复。已完成业务副作用不伪装成回滚，已发送机器人消息也不会自动删除。
- 其他事件：记录明确的 ignored 原因，不伪造卡片支持。
- `/action <nonce>`：进入现有审批控制事件，不作为模型输入；审批仍校验真实发起者、会话与授权版本。

外部用户标识为 `tenant_key:open_id`，外部会话标识为 `tenant_key:chat_id`。各组件只允许有限的字母、数字、下划线、连字符，冒号不会产生歧义。平台继续使用 HMAC 身份规则，包含平台 tenant_id、channel、binding、身份版本和会话代次；群聊默认 per_user，显式 shared 配置沿用既有策略；话题额外包含 thread_id。因此相同外部 ID 在不同企业、平台租户、通道、绑定或群聊下均不自动共享 Session。

账号凭据只用于认证，不自动授予聊天权限。常驻运行仍要求管理端授予 IM 成员 `chat` 权限；禁用租户、绑定或用户后，入库、执行、投递分别检查当前权限。只有隔离验收入口会为准确命中随机单聊口令的用户创建测试成员授权。

去重使用飞书 message_id，避免重投时 envelope event_id 改变导致重复模型调用。同一键不同正文仍拒绝。原始账号、会话回复上下文通过现有 ContextCipher 加密落库；header.token 不跨 IPC 传递。

## 3. 输出与平台差异

| 项目 | 企业微信智能机器人 | 飞书企业自建应用机器人 |
|---|---|---|
| 凭据与连接 | Bot ID / Bot Secret，官方协议长连接 | App ID / App Secret，官方 Python SDK 长连接 |
| 接收证明 | 连接认证 + 账号核对 | 连接认证 + App ID 核对 + 企业身份一致性 |
| 当前回复 | 既有 stream reply，最终文本 | 异步文本发送；话题内使用 reply |
| 平台回执 | 协议 ACK，不等于已读 | message_id，不等于已读 |
| 长文本 | 超出既有单 stream 限制明确拒绝 | 每片最多 3000 UTF-8 字节，按 Unicode 码点切分 |
| 去重 | msgid + 平台租户与绑定 | message_id + 平台租户与绑定 |
| 平台限制 | 依赖有效回复上下文与 SDK 协议 | 429 按 Retry-After 有界退避；其余结果按确认程度落账 |

飞书每片投递从 outbox_id + part_no 生成稳定 UUID，审批通知从 notice_id 生成稳定 UUID。已成功片段不重发，只有明确拒绝且可重试的片段才重试。429 最多等待 3600 秒；未知网络结果、5xx 或成功应答缺失 message_id 都标记 unknown，禁止自动重发。平台 UUID 作为额外去重措施，不能替代本地账本，也不宣称跨平台 exactly-once。

飞书当前完成最终文本异步回复，没有把模型内部 SSE 当成 IM 原生流式。入站图片/文件与入站撤回已接入；机器人主动发送图片/文件、删除已发送回复和卡片仍未实现。企微图片/文件入站使用官方 SDK 的加密下载接口；当前 SDK 未提供等价的消息撤回事件，因此不宣称企微撤回已实现。

## 4. 治理与观测

飞书复用既有租户 Filter、权限版本复验、工具白名单与二次确认、模型预算、费用结算、审计和 OpenTelemetry 入口。`im.callback → Inbox trace_context → Runner / Model / Session → Outbox → im.reply` 沿用既有传播，通道标签为 feishu；工具和后处理部分仍由既有实现负责。

SDK 默认日志可能包含签名 WebSocket URL 和原始 payload，因此子进程只导出固定 connected / failed 生命周期标记；HTTP、SDK 错误正文不进入日志或投递报告。凭据来自 `env://` SecretRef，本机配置只放被 Git 忽略的 `.secrets`；不要在命令参数、截图或报告中填写 Secret。Lark 默认日志处理器被替换，但没有修改 SDK 文件。

## 5. 配置与运行

飞书控制台：企业自建应用开启机器人能力，启用与当前场景相应的接收消息权限、以应用身份发送消息权限；事件与回调选择长连接，添加“接收消息 im.message.receive_v1”，发布应用并确保测试用户在可用范围内。部分控制台保存需要当时存在长连接，先启动验收，再保存并发布。

本机隐藏输入配置（已有文件不覆盖）：

```powershell
.venv\Scripts\python.exe -m trpc_service._cli configure-feishu --app-id <AppID>
```

常驻 ChannelBinding 配置项：`channel=feishu`，`transport=feishu_ws`，`external_account_id=<AppID>`，`credential_refs` 中 `name=app_secret` 对应 `secret_ref.uri=env://TRPC_FEISHU_APP_SECRET`。webhook_public_id 在这里是平台内部的路由绑定标识，不要求公网回调 URL。其余 tenant_id、binding_id、agent_app_id、启用状态与现有管理配置一致。

双通道隔离验收：

```powershell
.venv\Scripts\python.exe -m trpc_service._cli dual-im-e2e --test-timeout 600
```

默认加载 `.secrets/im.json` 和 `.secrets/feishu.json`，也可使用 `--secrets-file` 与 `--feishu-secrets-file` 指定本机文件。两路各自建立全新隔离 SQL 数据库，连接就绪后打印不同随机口令。用户分别单聊发送；每通道仅一条消息、最多一次模型调用、128 输出 tokens、0.50 USD 预算上限。不触碰常驻第二阶段服务或自动授权真实业务用户。

报告输出到 `reports/live-wecom-acceptance-*.json`、`live-feishu-acceptance-*.json` 和 `live-dual-im-*.json`。汇总双通道通过仅表示两条隔离真实文本链路通过；共用路由下的隔离由独立协议测试验证，不能把不同测试数据库当作生产租户隔离的证据。
