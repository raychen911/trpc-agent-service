# 第三阶段按序推进：SDK 契约与受预算保护的工具链路

本批对应用户“按顺序开始测试和开发”，继续遵守 [原始需求对照](第三阶段范围校准-原始需求对照-2026-09-06.md)。只使用官方 tRPC-Agent-Python；没有修改 SDK，也没有接入退款、订单等新增业务系统。

## 1. 第一项：官方 SDK 写入契约复核

2026-09-06 使用 `git ls-remote https://github.com/trpc-group/trpc-agent-python.git HEAD` 核对，上游最新提交仍为 `f05797d9f9dff2461922b5985aeccc1b636b7c8d`，与项目锁定版本及干净的 `.upstream-sdk` 基线一致。因此不存在可通过“再升级一次”消除的版本差距。

新增 `tests/e2e/test_sdk_write_contract.py` 和独立进程辅助程序：

- 旧进程先通过公开 Session API 读取原生快照，随后暂停。
- 平台数据库中的旧租约被明确置为过期，新 owner 取得更大的 fencing token，并写入新事件。
- 恢复旧进程，分别调用原生 `append_event`、`update_session`，检查是否拒绝旧 owner，且新事件仍在。
- 使用完全相同的事件 ID、时间戳和内容重试追加，检查是否返回幂等成功且仅保存一次。

真实 PostgreSQL / Redis 上的六个契约检查均复现已知缺口。测试使用 `known_gap` 标记；正常测试报告中的 **XFAIL 是缺口证据，不能计为功能通过**。加 `--strict-acceptance` 后这些检查会成为失败的发布条件。测试中的旧、新进程各有独立 SDK 实例和连接池，没有以进程内锁代替跨进程验证。

结论：平台租约和原生 SDK 事件 metadata 不能形成同一个底层原子写入条件。公共 `SessionServiceABC` 允许委托实现，但当前原生 SQL/Redis 服务没有暴露将平台 token 检查加入其原子提交的接口。现有生产 Runner 门禁继续保留；没有新增绕过开关。完整需求见 [SDK 边界说明](SDK原子写保护扩展边界-2026-09-05.md)。

## 2. 第二项：真实模型协议与工具装配

此前 OpenRouter 工厂只允许一次纯文本请求，会拒绝工具声明和工具结果历史。本批补充：

- `BudgetedOpenRouter` 接受服务端明确配置的工具名称和有限模型调用次数；默认仍是一次纯文本调用。SDK 重试、模型回退、额外插件仍不在该计费契约内。
- 每次模型调用独立预留完整上下文上限并按供应商 `usage.cost` 结算；工具描述、参数和结果包含在上下文额度内。后台摘要也计入同一次执行的共享调用次数和租户预算。
- 校验实际 HTTP 工具定义及历史调用的工具名称；不允许未登记工具、旧式函数接口或图片等未覆盖的计费类型混入请求。
- `assemble_tools` 统一装配现有资源工具、持久结果记录和治理 Filter。确认工具必须对应已登记的 `ActionDefinition`，只产生提案；缺少执行定义时报配置错误。审批结束当前轮次，后续执行继续由既有 ActionWorker 负责。
- `ConfiguredSummaryModel` 使用公开模型适配接口，为原生 SessionSummarizer 补齐明确的模型和计费配置，不改 SDK 摘要实现。

ServiceRuntime 复用工具装配函数，但其模型仍受原有 simulation / 生产门禁约束。上述变化没有把常驻双 Worker 自动切成真实模型。

## 3. 可运行的隔离链路

`AcceptanceRuntime.start(..., resources=...)` 新增服务端注入资源的测试方式，保持单进程、全新数据库、单个明确私聊口令的限制。没有新增从 IM 消息选择资源或任意模块的入口。已有 CLI 文本联调方式继续保持原行为。

本批集成链路为：

1. IM 回调归一化、权限绑定、持久化及重复抑制。
2. 官方 Runner 加载原生 SQL Session，并通过官方 PreloadMemoryTool 从当前用户 scope 读取已存记忆。
3. 模型产生 `write_artifact`，现有 S3ArtifactService 保存文件；模型再调用 `read_artifact`，读取实际保存结果。
4. 最终模型回复通过已有 IM 投递器发送。
5. 消费持久后处理任务，执行 SQL Memory 入库、受预算约束的原生摘要生成、原生 Session 更新和平台摘要水位记录。

新增 Memory 读写 Span。测试断言 IM、Runner、Tool、Session、Memory、模型响应、摘要和 IM 回复拥有同一 trace_id，并验证 Memory 查询实际发生在 Runner 执行之内。文件参数、消息内容及合成 API key 不进入这些 Span 的属性。

## 4. 验证边界

测试覆盖：

- 官方 SDK 的 HTTP/SSE 工具编解码、两个实际资源函数、原生 SQL Session / Memory、原生摘要和投递账本。
- 真实 MinIO 保存、读取及文件版本；租户外的文件 / Memory 查询被拒绝。
- 每次模型调用及摘要各有已结算记录，达到共享调用次数上限后不能再发请求。
- 首次模型应答缺少费用凭据时，文件写入没有发生，预留保留为待核对。
- 摘要缺少费用凭据时，已有前台回复不被重复投递，Memory 成功而 Summary 任务失败，不能声称后处理全部完成。
- 公共装配函数下的“提案—确认—执行”回归，缺少确认执行定义时拒绝装配。

本批模型供应商和 IM 平台端使用合成协议应答，**没有新增真实账号 IM 或付费模型工具实测**。真实后端专项使用独立 PostgreSQL、Redis、MinIO 容器；Session/Memory 工具链路部分使用原生 SQLite。不能把“真实 MinIO + 原生 SDK + 模拟模型/IM”写成完整生产端到端验收。

`flake8 trpc_service tests` 与 `git diff --check` 通过。测试结束已删除本批三个专用容器，原有第二阶段服务未改动。SDK 基线再次核验仍干净；没有提交或推送代码。工具测试全部使用合成模型应答，本批未产生新的真实模型费用。

## 5. Telegram 替代通道与下一步

保留企微，第二通道可选以下任一种，符合原要求允许“其他 IM”的范围；不要求三种全部开发。

| 通道 | 申请 / 参考入口 | 本项目当前状态 |
|---|---|---|
| 飞书 | [开发者平台](https://open.feishu.cn/)、[官方 Python SDK](https://github.com/larksuite/oapi-sdk-python) | 建议候选；账号、应用权限和适配开发待确认 |
| QQ 官方机器人 | [QQ 开放平台](https://q.qq.com/)、[腾讯官方接入参考](https://github.com/tencent-connect/openclaw-qqbot) | 可先用 QQ 了解申请；具体单聊 / 群能力以控制台开放范围为准，尚未适配 |
| 钉钉 | [官方 Stream 机器人创建说明](https://open-dingtalk.github.io/developerpedia/docs/explore/tutorials/stream/bot/java/create-bot/) | 需要组织开发权限及应用配置，尚未适配 |

已向用户询问选择；本批没有自动更换第二通道，没有把已有 Telegram 协议测试当作 QQ / 飞书实测。

后续顺序：补充实际资源写入的确认执行定义及常驻装配 → 完成必要后台租户授权和脱敏治理 → 补全审计字段、运维故障测试 → 选定第二通道开发并完成双通道实测 → 核心管理 UI 和原需求交付整理。原生写保护的生产阻塞独立保留。
