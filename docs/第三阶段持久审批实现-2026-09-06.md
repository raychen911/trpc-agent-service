# 第三阶段第四批：持久危险动作审批

**范围修订：**依据用户后续“严格按原来的需求”要求，文末商业业务接线、卡片、委派/双人审批、专用人工核对接口和新总结轮次均不再自动作为必做项。以 [原始需求对照](第三阶段范围校准-原始需求对照-2026-09-06.md) 为准，保留原需求的可执行工具、二次确认、权限和故障处理。

依据主开发方案 W06，并接入 W05 Filter、W10 后台接口和 W09 队列观测。本批交付审批执行框架及测试，不把测试退款工具当作真实退款系统接入，也不表示第三阶段全部完成。

## 1. 已落地的链路

```text
受信任的 IM 输入 → 官方 Runner → ProposalTool
  → 同事务：PendingAction + 创建审计 + 加密确认通知
  → skip_summarization：当前 Agent 轮次结束
  → Channel owner 投递确认说明和 /action 命令
  → 用户批准 / 拒绝 / 取消
  → 同事务：动作状态 CAS + 执行任务 + 审计 + 回调去重 + polling offset
  → action-worker：会话租约 + 当前权限/配置 + 外部对象前置条件
  → ToolGovernanceFilter → DurableTools → 已注册业务函数
  → 工具结果持久化 → 动作结果与通知同事务提交 → Channel owner 投递结果
```

代码在 `trpc_service/governance/actions.py`、`action_tools.py`、`action_worker.py`、`action_delivery.py`、`action_management.py`、`action_process.py`。

使用官方 SDK 的 `FunctionTool`、`InvocationContext.event_actions.skip_summarization`、`add_filters` 与 `run_filters`。不修改 SDK，不保持一个等待用户回复的执行协程。Agent 的待确认工具响应投影为带 action_id 的轮次终点；普通 Outbox 校验对应数据库动作后内部完成，确认说明由专用加密通知队列发送。

## 2. 身份和不可变参数

- 每个 tenant/execution 最多一个动作，由数据库唯一约束与租户/输入行锁保证。相同调用重复创建返回原记录，参数、摘要或工具版本变化则拒绝。
- 工具目录按 `(tenant_id, tool_name, tool_revision)` 注册。模型不能传入目录、批准者或执行许可。
- 参数和对象前置条件加密保存，并共同计算哈希；nonce 只保存哈希，原值仅存在于加密确认通知中。接口不返回参数、nonce、回调上下文或密文。
- 首版规则是**具有 chat 和 approve 授权的原发起人确认自己的指定动作**。不同意把群中其他成员、普通聊天授权或平台 operator 身份自动当作审批权限。委派及双人复核规则仍待实现。
- 确认绑定租户、Binding、chat/topic、指定 actor、nonce、revision、有效期、原配置和策略哈希。普通“确认”文字不会批准动作；只有精确 `/action a:...`，或携带相同引用的受验证卡片回调，进入决策路径。
- 排队后再次检查申请人和批准人的当前成员 epoch、应用启用状态、当前发布版本、策略、对象版本。模型传入 `confirmed=true` 不会绕过 Filter。

命令引用首版长 59 字节，适合 Telegram callback_data 的 64 字节限制，但本批确认 UI 采用明确文本命令，未交付卡片渲染和按钮交互体验。通知摘要必须由部署方的 `prepare` 产生，只允许 operation/target/impact/amount/currency 五个公开字段；业务适配器必须使用脱敏展示名和不敏感引用，不能直接复制原始参数或凭据。

## 3. 独立执行和恢复

`ActionDefinition` 包含声明名称和版本，以及三个部署方实现的函数：

| 函数 | 契约 |
|---|---|
| `prepare(arguments)` | 无业务副作用；返回规范参数、不可变前置条件、公开摘要；拒绝未支持的参数，不让模型选择权限 |
| `await check(arguments, preconditions)` | 执行前只读核对外部对象版本 |
| `await execute(arguments, preconditions, action_id)` | 使用 action_id 作为稳定业务幂等键，**在外部写入中原子验证前置条件**（例如 If-Match/CAS）；只返回可安全持久化的结果引用/回执 |

`check` 与外部写之间存在时间间隔，因此只做 check、随后无条件写入的适配器不满足契约。真实业务工具必须针对目标系统另做并发版本与回执验收，不能仅凭本框架测试宣称外部副作用 exactly-once。

执行器使用 SessionCoordinator 串行化同一会话；资源检查后续租，并在限定超时内执行。已批准动作通过内部 Filter 许可执行，许可不放入模型工具参数。未确认的原始执行不能继续调用 DurableTools；装配时同时给模型和普通工具安装 ConfirmationBoundaryFilter。

网络副作用之前写工具调用意图。进程中断后，只有匹配 tenant、工具名、参数哈希、成功状态和结果哈希的完整账本证明，才恢复为 succeeded。没有完整证明则为 unknown_outcome，不自动再次调用业务函数。工具成功后通知失败仅影响通知状态，不重跑工具。

所有通知由现有账号 owner 顺序消费。发送前记录 sending；丢 ACK 或崩溃留下的发送归为 unknown_outcome，明确可重试的拒绝有上限退避。权限撤销和过期确认不继续发送；过时的“等待执行”说明被跳过。

企微执行结果使用批准回调的新 req_id，不抢先用“批准已入队”结束该响应流。Telegram 可以发送入队说明和最终结果。企微真实回复窗口、长时间排队后的主动通知、卡片更新及失效上下文恢复尚待平台联调；当前失败保持可查看状态，不伪造成功。

## 4. 部署与后台接口

独立进程要求 PostgreSQL，SQLite 只用于组件/SDK 契约测试。环境变量：

```text
TRPC_DATABASE_URL=<共享平台 PostgreSQL 连接>
TRPC_IM_CONTEXT_KEYS=<与 channel 相同的加密密钥组>
TRPC_ACTION_CATALOG_FACTORY=<部署方模块>:<目录工厂函数>
```

工厂接受 Database，返回显式非空的 `(tenant, name, revision) → ActionDefinition` 字典。它是部署代码配置，HTTP/模型不能指定模块。本批不默认安装退款、删除等实际业务工具。

```powershell
.venv\Scripts\python.exe -m trpc_service._cli action-worker
```

进程包含数据库故障退避、停机信号、有限排空、取消后账本恢复和现有 heartbeat。Channel 进程自动消费 action_notices。原有生产 Runner 的 SDK Session 原子 fencing/CAS 门禁保持不变；这里没有提供绕过开关，也没有把纯文本联调入口改成危险工具开放入口。

后台 API：

| 方法和路径 | 行为 |
|---|---|
| `GET /admin/tenants/{tenant}/actions` | 分页、状态过滤；只返回公开摘要与状态 |
| `GET /admin/tenants/{tenant}/actions/{action}` | 动作、执行任务、通知状态；不返回敏感参数 |
| `POST .../{action}/decision` | decision、nonce、expected_revision；受服务端绑定身份和当前 IM 授权限制 |

继续使用既有 operator Bearer 认证。`TRPC_ADMIN_ACTOR` 是部署时绑定的身份，普通平台 operator 不自动拥有 IM 审批权；请求内 actor_id 被拒绝。该机制用于受信运维接口，**不是未来管理 UI 的 OIDC/RBAC 方案**。浏览器必须通过身份提供方与租户角色映射取得可信 principal，不能将共享 operator Token 嵌入前端。

新增 actions/action_jobs/action_notices 的队列数量、活跃量、失败量及积压年龄，审批审计关联原请求 trace/execution，执行和通知分别产生 action.execute、im.action_reply Span。参数、nonce、消息正文和依赖异常原文不作为指标标签或 Span 属性。

## 5. schema 5 升级

新增 pending_actions/action_jobs/action_notices。新空数据库初始化为 schema 5。版本 3/4 必须停写、核实备份后显式执行：

```powershell
.venv\Scripts\python.exe -m trpc_service._cli upgrade-schema --offline --backup-id <已验证备份标识>
```

版本 4 到 5 保留原账本、价格和配置；活跃账号 owner、Session writer 或在途模型 attempt 阻止升级。工具不能证明外部进程已经停机，不能把 --offline 当作在线迁移。未修改运行中的第二阶段数据库或历史真实联调库。

## 6. 验证与剩余工作

专项测试覆盖原生 Runner 提案后结束、批准前零业务副作用、当前权限/参数/会话校验、重复审批、事务回滚、超时不重放、成功后崩溃恢复、篡改回执拒绝、通知不盲重发、后台身份伪造拒绝、旧版本升级。PostgreSQL 专项覆盖并发提案/批准只建一条任务、两个执行器只有一次业务调用。

最终证据：

- `reports/phase-three-actions-regression.xml`：257 项，249 通过、8 跳过、0 失败。专用 PostgreSQL 中的 IM、预算、审批并发测试实际执行。
- `reports/phase-three-actions-focused.xml`：27 项通过，包含企微批准回调上下文切换、审批/后台/迁移与两个 PostgreSQL 并发场景。
- `reports/phase-three-actions-postgres.xml`：单列两项 PostgreSQL 审批并发测试。
- `flake8 trpc_service tests`、`git diff --check` 和 `action-worker` CLI 注册检查通过。

8 项跳过需要既有真实六后端、MinIO、迁移或 TCP 故障环境，不能计为通过。新审批测试使用合成消息和测试业务函数，不产生真实退款/删除，也没有追加真实模型费用。既有 FastAPI/PTB 弃用提示以及 Pydantic 字段属性提示仍有报告记录。
